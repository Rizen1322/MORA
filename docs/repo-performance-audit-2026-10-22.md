# Аудит MORA / AutoMix — 22 октября 2026

Что делает репозиторий: персональный музыкальный плеер с локальной медиатекой, сетевыми источниками, рекомендациями и автоматическим DJ-сведением. Сервер Fastify/SQLite готовит аудио, React/AudioWorklet воспроизводит его; Electron упаковывает Windows-приложение, Swift-клиент использует отдельную сборку планировщика.

Нагрузка для оценки: один пользователь, сотни — несколько тысяч треков, длительная работа радио, импорт плейлистов и допустимых длинных записей. Это аудит основных потоков всего собственного приложения, а не обещание построчного прочтения каждого файла. Три агента независимо проверяли AutoMix, серверные ресурсы и web/desktop/iOS; основной агент проверял общую архитектуру, БД, маршруты и воспроизведения. Код приложения и пользовательские данные не изменялись.

P1 — исправить в первую очередь; P2 — исправить планово или до выпуска затронутой платформы. Измерения относятся к временным синтетическим стендам, если явно не указано другое. Оценки гигабайтов по размерам массивов не являются замерами RSS процесса.

**Исправить в первую очередь**

1. **[P1] Ошибка записи скачиваемого файла завершает backend.** `apps/server/src/providers/types.ts:99–123`.
   - **Что это:** общий загрузчик Subsonic, Jamendo и Audius пишет ответ в файловый поток.
   - **Проблема:** у `WriteStream` нет обработчика `error`; ожидание `drain` тоже не обрабатывает ошибку. Изолированный вызов с недоступной для записи целью завершил дочерний Node-процесс кодом 1 с `Unhandled 'error' event / EISDIR`, вместо попадания в окружающий `catch`.
   - **Исправление:** использовать стандартный `pipeline()` с поточной проверкой размера. Ошибка должна завершать оба потока и удалять незавершённый файл; добавить тест ошибки записи.
   - **Если оставить:** ошибка доступа или заполненный диск могут оборвать весь сервер и воспроизведение, а не только одну загрузку.

2. **[P1] Обновление импортированного плейлиста портит его после ручной перестановки.** `apps/server/src/public/imports.ts:146–154,172–195`; `apps/server/src/routes/library.ts:219–228`.
   - **Что это:** импорт связывает исходную строку с записью плейлиста через вычисленную позицию `row.position * 10`.
   - **Проблема:** ручная сортировка меняет позиции на последовательные числа, после чего импорт обновляет уже другую запись или вставляет дубликат. Воспроизведение: `[Alpha, Beta]` → перестановка → «Обновить плейлист» → `[Alpha, Alpha, Beta]`; «Пропустить» уже добавленную строку также не удаляет её из плейлиста.
   - **Исправление:** сохранять стабильный `playlist_tracks.id` для строки импорта и менять/удалять запись по нему. Проверить перестановку, повторы одного трека и последующий пропуск.
   - **Если оставить:** пользовательские перестановки и состав плейлиста будут незаметно изменяться при работе с отчётом импорта.

3. **[P1] Перенос работающей медиатеки может успешно завершиться без части аудиофайлов.** `apps/desktop/src/migrate.mjs:25–50`.
   - **Что это:** сначала перечисляются и копируются файлы, затем делается согласованный снимок SQLite.
   - **Проблема:** добавленный исходным сервером во время копирования трек попадает в снимок БД, но отсутствует в уже зафиксированном списке файлов. Агент воспроизвёл перенос с кодом 0: в новой БД два трека, скопирован один файл; `integrity_check` этого не замечает.
   - **Исправление:** сначала фиксировать снимок БД, затем копировать его данные и проверять наличие всех перенесённых managed-файлов перед отметкой успеха. Если исходник меняется и нужный файл исчез, завершать перенос ошибкой, сохраняя прежнюю медиатеку.
   - **Если оставить:** приложение покажет успешный перенос, но часть новых путей будет вести к отсутствующим файлам. Исходная библиотека при этом остаётся на месте.

4. **[P1] Ошибка публикации переноса не восстанавливает текущую медиатеку.** `apps/desktop/src/main.mjs:454–470`.
   - **Что это:** текущая папка переименовывается в backup, после чего staging должен занять её место.
   - **Проблема:** если второе переименование не удалось, `catch` удаляет staging и запускает backend без восстановления backup. Backend создаёт новую пустую библиотеку; постоянное уничтожение исходных файлов здесь не утверждается — они остаются в backup.
   - **Исправление:** хранить путь backup и возвращать его на место при неудачной публикации. Не удалять готовую staging-копию, пока восстановление не завершилось; проверить отказ именно второго `rename`.
   - **Если оставить:** после файловой блокировки или ошибки диска пользователь получает пустое приложение и должен восстанавливать библиотеку вручную. Вывод подтверждён ветками кода, инъекция отказа не запускалась.

5. **[P1 для длинных записей] Анализ структуры требует память пропорционально квадрату длительности.** `packages/core/src/mir/repetition.ts:5,105,136–151,192–200`; `apps/server/src/analysisWorker.ts:40`.
   - **Что это:** структура песни определяется сравнением каждого полусекундного кадра с каждым другим.
   - **Проблема:** для часа получается 7200 кадров: одна Float32-матрица — 197,8 MiB; исходная матрица и строки `repetitionPaths` вместе — около 396 MiB, плюс примерно 49 MiB элементов сортируемого массива, PCM и спектр. Для двух часов только две матрицы — около 1,54 GiB; два analysis worker могут работать одновременно, ограничения длительности здесь нет.
   - **Исправление:** ограничить число кадров структуры, увеличивая временной шаг на длинных файлах; длительности сглаживания и повторов пересчитать из секунд в кадры. Добавить проверку памяти на длинном синтетическом входе.
   - **Если оставить:** импорт длинного DJ-сета вызывает большой расход RAM/CPU и может закончиться нехваткой памяти. Это расчёт размеров реально создаваемых массивов; аварийный многочасовой прогон не запускался.

6. **[P1 для длинных записей] Восьмисекундные окна Demucs не ограничивают память всей задачи.** `tools/separate-vocals.py:48–51,81–98,175–178`.
   - **Что это:** модель обрабатывает окна, но декодирование, нормализация и сборка вокала выполняются над полной записью.
   - **Проблема:** одновременно удерживаются полный `raw`, копия `audio`, `normalized`, `output` и `weights`. Для часа stereo 44,1 kHz это около 5,7 GB до дополнительного результата деления и без модели; `block_power()` затем создаёт большие временные float64-массивы.
   - **Исправление:** сначала освободить `raw` после копирования и считать мощность блоками. Для полноценной поддержки длинных записей декодировать и собирать результат блоками/через файл с отображением в память, не держать все копии в RAM.
   - **Если оставить:** часовой сет способен занять несколько гигабайтов даже при небольшой модели и коротких inference-окнах. Размеры рассчитаны по массивам, запуск реальной модели на часовой записи не выполнялся.

7. **[P2] Список теряет прокрутку, если сначала был пустым.** `apps/web/src/components/TrackList.tsx:28–46,57,77`.
   - **Что это:** виртуализация показывает только строки около видимой области и слушает прокрутку родителя.
   - **Проблема:** при первом `tracks=[]` DOM-элемента с `ref` нет, effect выходит; после загрузки стабильный `ref` не меняется и подписка не появляется. Сценарий: открыть Library/Любимое до загрузки и прокрутить большой список до первого запуска аудио — за первым диапазоном видна пустота; аудиотики могут маскировать ошибку рендерами.
   - **Исправление:** сохранять контейнер с `ref` и в пустом состоянии либо подписываться при появлении элемента. Нужна проверка `empty → loaded → scroll`.
   - **Если оставить:** часть медиатеки невозможно нормально просмотреть в обычном сценарии первого открытия. Причина подтверждена lifecycle-кодом; браузерное воспроизведение не запускалось.

**Исправить планово**

8. **[P2] Сборка медиатеки тормозит сервер, особенно с реакциями Яндекса.** `apps/server/src/library.ts:463,525–560`; `apps/server/src/yandex-reactions.ts:119–130`; `apps/server/src/routes/library.ts:34–37`.
   - **Что это:** `listDTO()` собирает весь каталог для ответа API; даже запрос одного трека вызывает её целиком.
   - **Проблема:** на трек идут дополнительные SQLite-запросы, а поиск реакции через `substr/instr` сканирует таблицу синхронизации. Синтетический стенд с заполненными реакциями Яндекса: 277 треков — 13–14 мс, 1000 — 89–95 мс, 3000 — 582–646 мс синхронной работы основного потока, без HTTP и разбора ответа клиентом.
   - **Исправление:** пакетно прочитать источники и реакции, собрать карты один раз на ответ; одиночный DTO получать отдельно. Для поиска по базовому ID использовать индексируемое поле/выражение или ту же пакетную карту.
   - **Если оставить:** обновление библиотеки на нескольких тысячах треков задерживает другие API-запросы и подготовку PCM. Сотни текущих треков сами по себе не доказывают многосекундную задержку.

9. **[P2] Компактизация вокала блокирует основной поток и держит несколько полных копий.** `apps/server/src/stems.ts:332–349`.
   - **Что это:** после отделения вокал переводится из float32 в проверенный компактный s16-кэш.
   - **Проблема:** одновременно живут `src`, `q`, `back`; три больших цикла выполняются в основном потоке Node. Для пяти минут это около 212 MB буферов; self-check агента на минутной партии дал 193 мс общей работы и 115 мс максимальной задержки event loop.
   - **Исправление:** читать, конвертировать и проверять блоками; тяжёлую операцию выполнять в worker. Сохранить существующую проверку точности и атомарное переключение метаданных.
   - **Если оставить:** завершение подготовки вокала вызывает рывки API и всплески RAM, особенно на длинных треках.

10. **[P2] Пауза известной офлайн-загрузки не останавливает передачу.** `apps/server/src/public/downloads.ts:173–178`; `apps/server/src/library.ts:392–400`; `apps/server/src/public/provider.ts:283–307`.
    - **Что это:** повторная загрузка известного трека с вытесненным аудиокэшем идёт через `resolveMediaPath()`.
    - **Проблема:** `AbortSignal` Downloads туда не передаётся, у реального transfer другой контроллер. Две приостановленные такие загрузки продолжают сеть и удерживают оба слота до окончания; имеющиеся download-race tests покрывают ветку нового трека через `prepare`.
    - **Исправление:** передавать отмену подписчика по цепочке загрузки и использовать существующий `SharedPreparation`. Отмена офлайн-задачи не должна прерывать тот же transfer, если его ещё слушает плеер.
    - **Если оставить:** интерфейс уже показывает паузу, но сеть занята и следующие загрузки не стартуют.

11. **[P2] Импорты удерживают память без ограничения до перезапуска.** `apps/server/src/public/imports.ts:47–63,94–102,203`.
    - **Что это:** `jobs` хранит отчёты, `searchCache` — Promise с полными результатами поиска.
    - **Проблема:** ограничение 20 действует только при записи в БД; успешные результаты поиска никогда не удаляются. Self-check: 25 импортов дали 25 отчётов в RAM против 20 в БД и 25 кэш-записей; после удаления всех отчётов 25 результатов остались удержаны.
    - **Исправление:** ограничить завершённые отчёты и убрать вечный поисковый кэш, переиспользовав ограниченный кэш/объединение запросов `PublicMusic`. Либо очищать результаты после использующих их активных импортов.
    - **Если оставить:** массовый перенос плейлистов постепенно увеличивает память; сборщик мусора не освобождает объекты, пока на них ссылается карта. Скорость роста RSS отдельно не измерялась.

12. **[P2] Каталог публикует одинаковое состояние на каждом аудиотике.** `apps/web/src/lib/catalog-player.ts:48,53–55,142–164`; `apps/web/src/store/catalog.ts:37`; `apps/web/src/pages/Search.tsx:56`.
    - **Что это:** `pump()` поддерживает запас из двух следующих треков.
    - **Проблема:** даже при готовом запасе `finally` создаёт новый `idle` snapshot и уведомляет React примерно 20 раз в секунду. Изолированный fixture настоящего класса: 100 тиков неизменной очереди → 100 уведомлений, JSON состояния до/после одинаков.
    - **Исправление:** выходить из `pump`, если пополнение не требуется, либо не публиковать patch без изменений. Закрепить тестом отсутствия лишних уведомлений.
    - **Если оставить:** поиск/каталог тратит CPU на повторные рендеры без новой информации.

13. **[P2] Открытая очередь пересоздаёт все строки на каждом аудиотике.** `apps/web/src/components/QueuePanel.tsx:8,14,60`; `apps/web/src/pages/Library.tsx:139`.
    - **Что это:** пользователь может поставить всю медиатеку в очередь и открыть панель будущих треков.
    - **Проблема:** панель подписана на весь `player`, заново проходит всю очередь и рендерит все будущие строки без виртуализации. При нескольких тысячах песен это тысячи DOM-строк и повторная работа примерно 20 раз/с.
    - **Исправление:** подписываться только на нужные поля, а строки обновлять по queue/index/status. Ограничить видимый диапазон по уже существующему подходу `TrackList`, без новой библиотеки.
    - **Если оставить:** большая очередь создаёт заметную лишнюю работу React и расход памяти DOM. Точные CPU/GPU и время кадра не измерялись.

14. **[P2] Онлайн-радио бесконечно накапливает проигранные записи.** `apps/web/src/lib/catalog-player.ts:35,67,71–73,122–137`; `apps/web/src/lib/radio.ts:85–87`; `apps/web/src/audio/controller.ts:1136–1147`.
    - **Что это:** онлайн-радио дополняет сессию новыми кандидатами и добавляет их в очередь.
    - **Проблема:** `session.items`, прошлые элементы очереди и `prepared` растут без очистки; `matches()` ещё копирует растущую очередь при тиках. Симуляция агента после 1001 песни: queue/session/prepared по 1001 элементу; после cancel кэш prepared сохраняет 1001 запись.
    - **Исправление:** ограничить историю и удалять потреблённую часть сессии с корректировкой курсоров; ограничить prepared. Запрет повторов хранить отдельно в ограниченной истории идентификаторов.
    - **Если оставить:** длительная сессия радио увеличивает RAM и объём работы на каждом тике. Конкретное время до нехватки памяти не измерялось; это не утверждение об утечке самих PCM-буферов.

15. **[P2] Отмена анализа теряется до запуска и не прерывает вычисление MIR.** `apps/server/src/analysis.ts:121–124,147–159`; `apps/server/src/analysisWorker.ts:23–29,83–88`.
    - **Что это:** удаление трека отменяет его фоновый анализ сообщением worker.
    - **Проблема:** пока ожидается `resolveMediaPath`, worker ещё не знает job и игнорирует cancel; затем `.then()` всё равно отправляет задание. Во время синхронного `acc.finish()` обработчик сообщений не исполняется, поэтому проверки `state.cancelled` не получают обновления.
    - **Исправление:** хранить состояние отмены и проверять его перед отправкой job. Для активного расчёта использовать общий атомарный флаг либо завершать и заменять worker, учитывая lifecycle дочернего ffmpeg.
    - **Если оставить:** уже ненужные/удалённые треки продолжают занимать сеть, RAM и CPU; особенно дорого это вместе с пунктом 5.

16. **[P2] Энергетические кривые постепенно расходятся с временной шкалой.** `packages/core/src/mir/spectral.ts:184–192`; `packages/core/src/mir/analyze.ts:169–170`.
    - **Что это:** RMS и waveform рассчитываются как кривая с частотой 20 точек/с.
    - **Проблема:** при 22050 Hz окно округляется с 1102,5 до 1103 отсчётов, но результат продолжает считаться строго 20 Hz. Self-check агента на 120 с дал 2399 вместо 2400 точек, подъём сигнала на 100 с отобразился на 99,95 с; накопленный сдвиг за час — около 1,63 с.
    - **Исправление:** вычислять границы каждого окна через `floor(c * sr / CURVE_RATE)` и количество точек через `ceil(length * CURVE_RATE / sr)`. Обновить `ANALYZER_VERSION`, чтобы не использовать старые результаты.
    - **Если оставить:** окончания и энергетические границы расходятся с beat/vocal timing, снижая точность выбора точек перехода.

17. **[P2] Одновременные загрузки адаптеров сталкиваются на одном `.part`.** `apps/server/src/providers/types.ts:106–119`; callers: `providers/subsonic.ts:180–186`, `providers/jamendo.ts:148–155`, `providers/audius.ts:114–119`.

    - **Проблема:** адаптеры не объединяют одновременные запросы, оба пишут `${file}.part`. В изолированном воспроизведении агента второй запрос закончил переименование, первый продолжил работу и получил `ENOENT`.

    - **Если оставить:** лишний трафик и случайные ошибки загрузки одного трека при нормальном параллельном использовании.

    - **Исправление:** пересобрать штатным `npm run ios:prepare`, затем запускать существующую проверку актуальности перед выпуском iOS. Исправлять копию JS вручную не нужно.
    - **Если оставить:** iOS будет планировать переходы по старым правилам, несмотря на обновление общего ядра.

**Что улучшить в AutoMix после исправлений**

Это предложения для сравнения и прослушивания, а не объявленные дефекты звучания. Отдельный агент прочитал планировщик, MIR, MixerCore, WSOLA, загрузку PCM и AudioWorklet; подтверждённой бесконечной утечки PCM не нашёл.

- **A. Проверять реальный вокальный режим существующим оценочным инструментом.** `tools/eval-transitions.ts:69–90` сейчас вызывает `analyzePcm()` и рендерит только исходное аудио, без измеренной `vocalActivity` и stem PCM. Подключить существующие stems/тайминги слов, отдельно оценивать результирующий вокал после `gain × mask`, остаток прежнего голоса, потерянные первые слова, провал громкости и fallback без stems. Использовать фиксированный набор реальных пар и оценки из `transition_log`, а не добавлять новую модель до проверки нынешней.
- **B. Различать уверенность в BPM и в начале такта.** В `packages/core/src/plan/planner.ts:381–388,1038–1049` уверенный пульс допускает длинный beatmatch, но начало такта может быть неуверенным. Уже имеющиеся проверки других техник показывают, что эти уровни уверенности стоит оценивать раздельно; улучшение требует прослушивания.

Расширять сравнение адресно на плохо оценённые пары и считать оценку после защиты слов, EQ и DJ-преобразований; сначала достаточно небольшого набора пар и существующих crossfade/beatmatch/drop/echo, без новой архитектуры и зависимостей.
