# План оптимизации MORA на ПК без ухудшения звука

Исследование от 22 октября 2026, выделенное из общего документа. Это план для текущих desktop/web/server/core и Python-подготовки, а не отчёт о выполненных изменениях.

Цель — уменьшить RAM, CPU, блокировки API и повторную подготовку, сохраняя нынешнее качество звука и переходов. Перенос приложения на iPhone вынесен в [отдельный план iOS](ios-automix-plan-2026-10-22.md).

**Актуализация после параллельных исправлений**

Сверено с текущим кодом и [отчётом исправлений](audit-fixes-2026-10-22.md). Повторная независимая проверка: typecheck проходит; полный Vitest — **810/810, 93 файла**. В исходниках и iOS bundle стоят am-analyzer-12 и am-planner-v11-dj-7. Это проверка кода и тестов, не прослушивание или замер установленного приложения.

| Направление | Что уже сделано | Что осталось |
|---|---|---|
| Сбои загрузки/переноса | pipeline, объединение загрузок, snapshot до копирования, rollback публикации | Сохранить тесты; не переписывать повторно |
| UI/библиотека | No-op guard каталога, узкие подписки/виртуализация очереди, пакет sources, одиночный DTO и индексируемый поиск реакций | Browser smoke на изолированном профиле; остаточные запросы Яндекса измерить |
| Кэши/история | Ограничены отчёты импортов, поисковый кэш, catalog session/prepared и radio seen | История transport в controller.ts пока растёт; старые import jobs без entryId небезопасно обновлять после перестановки |
| MIR | Не больше 2400 кадров структуры; исправлено время кривых, версия анализа 12 | Длинные записи после 20 мин используют более редкую сетку: музыкальная эквивалентность не доказана |
| Вокальная подготовка | Удалён raw, деление output на месте, power блоками; compaction по 1 MiB | Audio/normalized/output/weights остаются полноразмерными; глобальная нормализация создаёт временные копии |
| Отмена | AbortController до dispatch и атомарный cancel во время MIR; signal загрузок проведён до transfer | Совокупный ресурсный бюджет и готовность stems к переходу требуют отдельной проверки |

Лимит stems по умолчанию **2048 MiB** сохранён. По переданному отчёту повторный анализ библиотеки для am-analyzer-12 разрешён; в этой проверке сервер на пользовательском профиле и переанализ не запускались.

WAV в v2 рассчитаны по анализам версии 11. Они пригодны для обсуждения того снимка, но финальную приёмку текущих переходов нужно повторить на версии 12 с теми же парами, настройками и версиями stems.

**Что означает «без потери качества»**

| Класс изменения | Что можно обещать после проверки | Примеры |
|---|---|---|
| A. Те же операции и данные | Совпадают планы, события и PCM/байты кэша | Удаление лишних копий, UI/SQL, точное вычисление полосы матрицы, потоковая существующая квантовка |
| B. Та же модель/алгоритм, другая реализация | Численная и акустическая эквивалентность требует сравнения | Streaming reductions, C++/WASM, другой resampler/backend |
| C. Меняется алгоритм или точность | Нужен отдельный эксперимент; это не бесплатная оптимизация | Меньшая модель, INT8/FP16 без приёмки, меньше shifts/context, более редкий анализ структуры |

Зафиксировать один эталон ПК: версия кода и настроек, decoder/resampler, hash модели, precision, число shifts. Текущие CPU shifts=1 и CUDA shifts=2 — разные режимы; нельзя одновременно требовать побитового совпадения с обоими. Между платформами floating-point не гарантирует одинаковых результатов даже для математически одинаковых вычислений. [PyTorch: Numerical accuracy](https://docs.pytorch.org/docs/main/notes/numerical_accuracy.html).

Исправления музыкальных ошибок, например дрейфа временных кривых, принимать отдельными изменениями с обновлением версии анализа. Не смешивать их с обещанием неизменившегося результата оптимизации.

**1. UI, каталог и БД: принять сделанное и закрыть остатки**

No-op публикации CatalogPlayer, useShallow в QueuePanel, виртуализация, пакет источников и trackDTO уже реализованы. Полных сканов реакций Яндекса больше нет; несколько индексированных запросов на трек пока остаются. Ограничения session/prepared/seen и импортных отчётов тоже уже есть — не добавлять второй слой кэша.

Следующие проверки:

- Открыть изолированный временный профиль с фикстурами и проверить TrackList empty→loaded→scroll, длинную очередь, drag/drop и появление новых строк. Доступ к data-dev не нужен для такого smoke.
- Ограничить только прошлую историю бесконечного онлайн-радио в transport controller.ts, сохраняя index, next slots, переход, Previous и persistence. Будущие треки выбранного пользователем плейлиста не обрезать.
- Для legacy import jobs без entryId не угадывать запись по изменяемой позиции после ручной сортировки. Нужна безопасная привязка при доказанном совпадении либо явное прекращение обновления; не перезаписывать чужую строку.
- Остаточные запросы Яндекса оптимизировать после нового замера. Старые цифры до пакетной загрузки больше не описывают нынешний listDTO.

SQLite поддерживает индексы по выражениям, но выражение запроса должно совпасть с индексом; текущую уже индексируемую реализацию менять только по профилю. [SQLite expression indexes](https://www.sqlite.org/expridx.html).

**2. MIR: лимит памяти уже есть, точная оптимизация ещё полезна**

В repetition.ts уже введён MAX_FRAMES=2400 и hop=max(0.5, duration/2400). Одна Float32 матрица теперь ограничена примерно **22 MiB**. Тест двухчасового синтетического входа проверяет память, но не доказывает неизменность музыкальных решений.

Для записей до 20 минут шаг остаётся 0,5 s. Для более длинных шаг укрупняется: это изменение алгоритма структуры, а не только хранения. При требовании равного качества сравнить cue/paths/планы и прослушать длинные записи; сам лимит без безопасной замены не снимать.

Остаются точные кандидаты:

1. Вторая selfSimilarity для checkerboard читает лишь полосу шириной 4×KERNEL−1. Считать только её с прежним Float32 округлением и порядком суммы. KERNEL теперь зависит от hop — нельзя жёстко зашить старые 12/47.
2. В repetitionPaths после получения прежнего percentile использовать пять скользящих lag rows вместо хранения всей w. Проверить границы и адаптивные временные константы.
3. Pool хранить как исходные Float32 значения; точный выбор k-го элемента вводить отдельно при необходимости, без приближённой гистограммы.

Исходная s нужна последующему link(bounds); удалить её без замены доступа нельзя. Мой прежний self-check полосы дал побитовое совпадение на малых синтетических данных при KERNEL=12. Его надо расширить на адаптивные KERNEL до реализации.

Оценка 198→1,3 MiB относилась к одной матрице прежнего часового анализа без cap. Она не является нынешним RSS приложения или измеренным выигрышем после исправлений. Для восстановления полного временного разрешения длинных файлов в будущем можно исследовать блочное хранение s на диске, сохраняя строгий бюджет.

Приёмка: равенство novelty, paths, structure, cue candidates и планов для точных изменений; отдельно качество адаптивного анализа на длинных файлах.

**3. Demucs: закрытые копии не заменяют полный streaming**

Уже сделаны del raw, деление output на месте и block_power минутными блоками. Повторно внедрять эти пункты не нужно. Но audio, normalized, output и weights всё ещё размером во весь трек, а stereo_normalization создаёт полноразмерные временные массивы. Новое peak RAM надо измерить: старые оценки до этих правок устарели.

Следующий этап:

1. Декодировать один раз во временный float32-файл, читать ограниченными блоками.
2. Получить глобальные mean/stereo power и исходные 100 ms power bins без полноразмерных временных выражений.
3. Сохранить текущую модель, 8 s окна, 350 ms context, 25% overlap полезной части, shifts, padding и глобальную сетку окон.
4. Нормализовать только рабочее окно; output/weights собирать rolling buffer, публикуя отсчёты после последнего влияющего окна.
5. Сохранить нынешние activity/phrases и глобальные percentiles. Временные файлы учитывать в дисковом бюджете, публиковать артефакты атомарно.

Блочные reductions могут менять последние биты глобальной статистики и входа модели. Это кандидат на численную эквивалентность класса B, а не автоматическое обещание bit exact; нужен diff stems/activity/планов и прослушивание итоговых переходов.

Перекрытия помогают бороться с краями, но параметры официального примера не следует подставлять вместо текущих. [PyTorch Hybrid Demucs](https://docs.pytorch.org/audio/2.5.0/tutorials/hybrid_demucs_tutorial.html). Memmap позволяет читать фрагменты, но сам по себе не гарантирует потолок RSS и отсутствие больших временных массивов. [NumPy memmap](https://numpy.org/doc/stable/reference/generated/numpy.memmap.html).

Тёплый процесс модели исследовать только после раздельного замера import/model-load/inference/activity/write. Он экономит повторный запуск ценой постоянной RAM. eval() и inference_mode() уже есть; увеличение числа потоков может ухудшить общую нагрузку. [PyTorch multiprocessing](https://docs.pytorch.org/docs/stable/notes/multiprocessing.html).

**4. Stem cache и частоты: те же данные с меньшим количеством работы**

Compaction уже читает/конвертирует/проверяет блоками по 1 MiB, сохраняя прежние scale, Math.round и атомарную публикацию. Тест подтверждает те же байты. Это существенно ограничивает рабочую память; в worker операция пока не вынесена. Сначала измерить максимальную задержку event loop при реальном playback: await между I/O даёт другим задачам исполниться, но CPU-цикл каждого блока остаётся в основном потоке. Выносить его в worker при измеренной проблеме. [Node worker_threads](https://nodejs.org/api/worker_threads.html).

В `stems.ts:479` частота кроме 44100 Hz запускает ffmpeg на каждый диапазон. Сначала объединять одинаковые выполняющиеся запросы и кэшировать ограниченные aligned ranges; при подтверждённом выигрыше готовить один последовательный resampled stem для current/next, учитываемый в нынешнем PCM-бюджете.

Ключ включает content hash, **vocal revision**, sample rate и параметры фильтра. Нужны активные leases: eviction не должен удалить данные выполняющегося перехода. Сохранить gcd-aligned границы, поля вокруг диапазона, f32 и scale. Полное последовательное ресэмплирование сравнить с нынешним range reader на разрывах и EOF; сама смена стратегии ещё не доказательство побитовой эквивалентности.

Не менять swr на soxr, filter size, phase/cutoff или intermediate precision ради красивого benchmark: FFmpeg документирует эти параметры как часть поведения resampler. [Официальная документация FFmpeg в исходниках](https://github.com/FFmpeg/FFmpeg/blob/master/doc/resampler.texi).

**5. Аудиопоток и бюджет CPU**

Уже используются повторно выделенные большие DSP-буферы, оконный PCM и transfer list `[L.buffer,R.buffer]`. Переделывать это повторно незачем.

Остались мелкие выделения: `unity()/evalLanes`, `glide().map`, callback и EQ arrays в `renderDeck`. Заменить их scratch-полями деки и переиспользуемыми callback, сохраняя вычисления и разрезание блока на automation knots. Не уменьшать WSOLA search, transient protection или true-peak detector. Chrome связывает GC на AudioWorklet с риском glitches; увеличение ring buffer не увеличивает срок исполнения самого callback. [Chrome AudioWorklet design patterns](https://developer.chrome.com/blog/audio-worklet-design-pattern).

Отмена до dispatch и атомарный cancel во время MIR уже реализованы и покрыты тестами. Следующий шаг — совокупный admission через нынешние очереди: current/next PCM и нужные stems прежде библиотечного анализа/Whisper. Контроль ffmpeg lifecycle сохранить. Число воркеров выбирать по измеренной очереди/загрузке и доступной памяти, не добавлять отдельную тяжёлую службу планирования.

WASM/C++ — необязательный поздний этап desktop после этих изменений; перенос мобильного ядра описан в отдельном плане iOS. Emscripten поддерживает C/C++ AudioWorklet и runtime без временного JS-мусора, но остаются границы памяти/копии и необходимость профилировать. [Emscripten Wasm Audio Worklets](https://emscripten.org/docs/api_reference/wasm_audio_worklets.html). SharedArrayBuffer вводить только при измеренной необходимости: браузерная cross-origin isolation затрагивает загрузку внешних ресурсов. [MDN crossOriginIsolated](https://developer.mozilla.org/en-US/docs/Web/API/Window/crossOriginIsolated).

**Новые идеи AutoMix: что принять из исследования**

Источник предложений — [automix-ideas-2026-10-22.md](automix-ideas-2026-10-22.md). Это расширение возможностей, поэтому его качество и ресурсы принимать отдельно от оптимизаций с неизменным результатом.

1. **Сначала наблюдаемость готовности stems.** Записывать queued/inputReady/started/ready/planBuilt/armed/transitionStart, content hash, revision и причину fallback. Различать отсутствие расчёта, задержку источника, неполное покрытие и несовпадение версии. Прерывать модель ради next автоматически пока не стоит: без checkpoint прогресс теряется и очередь может голодать. Сначала измерить, затем выбрать безопасную границу отмены/перестановки.
2. **Затем воспроизводимые A/B на свежем анализе 12.** Пересчитать те же пары с одинаковыми данными и подготовить сравнение старого/нового плана на одном analysis. WAV v2 по версии 11 сохранить как исторические; новые оценки не смешивать без версий. В таблице исследования 50+10=60 оценок, 51 плохая+9 хороших=60, хотя написано 61: перед fitting пересчитать и убрать дубли между профилями.
3. **Drums/bass — хороший эксперимент, но не бесплатная оптимизация.** Модель уже выдаёт четыре источника; новый forward не нужен. Добавляются сборка двух результатов, перенос с GPU при его использовании, нормализация, конвертация, I/O, ресэмплирование и работа движка. Ускорение или рост только на «единицы процентов» пока не измерены. [Официальный pipeline PyTorch](https://github.com/pytorch/audio/blob/main/src/torchaudio/pipelines/_source_separation_pipeline.py).
4. **Сохранять оригинал опорным сигналом.** Формула m_o·original + Σ(m_k−m_o)·stem_k до общего WSOLA сохраняет оригинал при всех единичных масках и конечных данных. Не собирать unity из суммы оценённых stems; разделение и квантовка не гарантируют точную реконструкцию. Один WSOLA исключает независимый выбор offsets, но не устраняет ошибки самой модели и утечки при неединичных масках. Проверить scale/revision, противофазное stereo, seams, клиппинг, голос и transient alignment.
5. **Начать с офлайн bass-swap на трёх разных парах**, включая хорошо оценённую контрольную. Не добавлять сразу drums choreography, новые петли и новые веса одновременно. Сохранить нынешний LR4 путь как контроль; расширять кэш/движок только после сравнения.
6. **forced — неоднозначное действие, не дизлайк.** Логировать причину команды и момент перехода; не смешивать его с явной оценкой. Для подбора весов нужен baseline, сильное ограничение числа параметров и проверка на других парах; повторения пары и копии из двух баз не должны попадать одновременно в обучение и контроль. Bradley–Terry пригоден после получения настоящих парных предпочтений, а не автоматически для нынешних good/bad.
7. **Петли и render-veto — позднее.** Сначала посчитать долю коротких переходов, действительно ограниченных outro, и цену нескольких рендеров. Порог 3 LU сам по себе не отличает дефект сведения от естественной тихой части песни. Пресса про Apple и недоступная статья MixWeaver не заменяют проверку конкретного перехода.

Диск считать по длительности: s16 stereo 44,1 kHz — 176400 байт/с на партию. Для трёх минут одна партия ≈30,3 MiB, три ≈90,8 MiB; дополнительные drums+bass пяти таких песен ≈302,8 MiB. Пример «260 MiB» относится к другой средней длительности, это не лимит. Опциональные партии должны иметь byte budget внутри явно определённого суммарного бюджета; current/next временно защищены, закрепление всей offline-библиотеки не должно незаметно раздувать дополнительный кэш. Базовый лимит vocals 2048 MiB без отдельного решения не менять.

**Как доказать, что качество не проиграло**

Не писать новый тестовый микшер. Уже есть `renderTransitionOffline`, `tools/check-playback-release.ts` с настоящими stems, `tools/audit-library.ts` с voice-tail режимом и core golden/DSP tests. `eval-transitions.ts` сам по себе анализирует только original — использовать его вместе с существующими stem-aware инструментами, а не считать все проверки отсутствующими.

Зафиксировать ограниченный корпус: раннее первое слово B, длинный голос A, плотный бас/слабая доля, live tempo, тихое вступление, decoder overs, stereo/antiphase, loop/echo tail и fallback без stems. Сохранять исходные данные, analysis, vocal PCM/scale, настройки, окончательный plan и reference render.

| Проверка | Условие приёмки |
|---|---|
| Точные изменения A | Те же analysis/plan/events и те же PCM/байты; не учитывать только явно недетерминированные диагностические времена |
| Численные изменения B | Отдельно diff/SNR/null test компонентов, сохранение временных границ, громкости, true peak, limiter reduction и слышимого вокала; пороги выбрать по эталону до переключения |
| Realtime | p50/p95/p99/max render time относительно реального `frames / sampleRate`; ноль новых underruns в одинаковом сценарии; не ограничиваться средней загрузкой CPU |
| Память | Peak и steady RAM всего дерева Electron/backend/ffmpeg/Python; временный диск; отсутствие роста после десятков переходов и длинного радио |

Порог ровно «1e−6» из одного unit test нельзя объявлять общим стандартом для всех ресэмплеров/нейросетей. Численные метрики не заменяют слепое A/B: одинаковый LUFS может скрывать потерянное слово или неверную сильную долю. Для измерения использовать нынешние BS.1770 loudness/true-peak проверки, для прослушивания — скрытый ПК-эталон и одинаковую громкость; формальный MUSHRA требует собственной процедуры. [ITU BS.1770](https://www.itu.int/rec/r-rec-bs.1770/_page.print), [ITU BS.1534](https://www.itu.int/rec/R-REC-BS.1534/en).

**План реализации оставшихся этапов**

1. Зафиксировать эталон am-analyzer-12/am-planner-v11-dj-7 и реальную готовность stems; не смешивать новые решения со старыми WAV v2.
2. Принять browser UI на изолированных фикстурах и закрыть legacy import/transport history. Уже исправленные пункты аудита не переписывать.
3. Ограничить оставшуюся RAM подготовки: global normalization и streaming Demucs; отдельно принять численные различия и результат на слух.
4. Сократить матрицы MIR точно относительно нынешнего hop; отдельно проверить качество уже введённого adaptive hop длинных записей.
5. По профилю внедрить resample cache, совокупный admission и при необходимости worker compaction/тёплый процесс.
6. Отдельным офлайн-экспериментом проверить drums/bass на трёх парах; после положительного A/B решать о расширении production-контракта. Петли, fitting весов и render-veto — последующие независимые проверки.

Повторный анализ для версии 12 отмечен в переданном отчёте как разрешённый. Этот план и текущая проверка сами не запускают пользовательский переанализ, модель, сервер или изменение медиатеки.

Вердикт: сначала убрать лишнее хранение и повторную работу, затем проверять более дорогие изменения реализации. Не уменьшать качество алгоритма, чтобы скрыть стоимость подготовки.

Код приложения и пользовательские данные этим документом не меняются. Не выполнены benchmark модели с весами и длительное прослушивание; локально проверена математика полосовой novelty, остальные величины выигрыша требуют измерений.
