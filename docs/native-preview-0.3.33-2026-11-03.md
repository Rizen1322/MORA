# Native Preview 0.3.33: фоны, дизлайки, «медленный Яндекс»

## Фоны перестали реагировать на музыку

SSE-канал аудиособытий закрывал соединение, когда `write()` возвращал `false`. Это обычное противодавление, а не обрыв: всплеск waveform-пакетов отключал поток, и визуальный анализатор переставал получать данные. Теперь waveform-пакеты пропускаются, пока буфер ждёт `drain`; соединение закрывается только при превышении 256 КиБ или настоящем закрытии. Тест `apps/desktop-tauri/test/audio-events.test.ts` шлёт всплеск через настоящий HTTP/SSE и проверяет ненулевой спектр; до исправления он падал с `other side closed`.

## Дизлайки

Сохранённые дизлайки доходят до нативного владельца очереди напрямую из backend (Tauri: подписка на события библиотеки; Electron: сообщение `reactions` в main), без участия страницы. Нативная очередь убирает такие треки из будущих записей, повтора, передачи очереди, пополнения волны, восстановления и «Назад»; подготовленный следующий трек снимается; дизлайк текущего трека сразу переключает на безопасный следующий без микса, а при его отсутствии ставит паузу. Маршрут волны Яндекса перепроверяет локальные дизлайки после ответа провайдера. Страница в десктопе не выполняет второй пропуск: при нативном хосте `applyDislike` в контроллере ничего не делает. События библиотеки при импорте приходят на каждый трек, поэтому полный пересчёт списка дизлайков объединяется в один за 100 мс.

## «Песни Яндекс Музыки загружаются медленно» (по «Слушать»)

Профиль Native Preview (копия БД, только чтение): подключённого аккаунта Яндекса нет, все 25 треков — записи YouTube из файлового импорта плейлиста. Папки `remote/yandex` нет. Значит, в Preview «треки Яндекса» воспроизводятся через путь YouTube (yt-dlp), а не через загрузку Яндекса.

В реальной сессии анализ первого трека начался примерно за 1.8 с до звука; анализ ставится в приоритет при запросе `pcm-source`, так что серверная часть от запроса до звука заняла около 1.8 с. Момент нажатия «Слушать» в профиле не записывается, поэтому промежуток между нажатием и запросом установить нельзя.

Контролируемый замер на временном профиле (тот же код сервера, упакованные yt-dlp/ffmpeg/Rust-помощники, две публичные записи из этого плейлиста, 6 прогонов, без воспроизведения):

| | Первый PCM | Полная загрузка |
| --- | ---: | ---: |
| 5 прогонов | 1.9–2.5 с | 2.1–2.7 с |
| 1 прогон | 2.5 с | 180 с, остановлено тайм-аутом yt-dlp |

Старт воспроизведения прогрессивный и стабильно занимает около 2 с. Редкое замедление CDN YouTube наблюдается и на транспорте yt-dlp, поэтому вывод отчёта 0.3.32 о медленной Rust-передаче, сделанный по одному прогону, не доказан. Маршрутизация YouTube не менялась. Если нужна точная локализация на стороне интерфейса, нужна трассировка времени от нажатия до `startSource`.

Для настоящих треков Яндекса (при подключённом аккаунте) «Слушать» в каталоге ждёт полного импорта: метаданные, download-info, XML, весь MP3 через Rust, ffprobe, SHA-256, обложку (до 4 с) и перезагрузку библиотеки. Живой замер без использования учётных данных пользователя невозможен, поэтому этот путь не менялся.

## 0.3.34: запуск «Моей волны» Яндекса и «Далее»

После подключения аккаунта профиль Preview (копия, только чтение) показал: 52 лайка импортированы примерно за 56 с двумя потоками, то есть около 1.5 с на полный MP3 320 кбит/с (4–11 МБ) вместе с проверкой и обложкой. Первый трек волны начал играть через несколько секунд после нажатия. Медленным перенос с Rust-транспортом в этой сессии не был.

Трек волны начинает играть только после полного импорта: метаданные, download-info, XML, весь MP3, ffprobe, SHA-256, обложка (до 4 с, после звука) и запись в медиатеку. Пополнение на 3 трека шло в два последовательных раунда (2 параллельно, затем 1), и ответ возвращался только после обоих. Исправлено:

- Обложка больше не задерживает импорт; её загружает `ensureCover` по сохранённому `coverUrl` сразу после записи трека.
- Пополнение волны Яндекса ограничено двумя треками, то есть одним параллельным раундом.

Прогрессивное начало воспроизведения трека Яндекса до окончания загрузки не реализовано. После закрытия Preview пользователем скрытые `shell-smoke` и `autonomy-smoke` прошли; извлечённый из NSIS EXE (SHA-256 `d497a473eb53ae57ad7c2940b0c6a1fff4cc47949df5a3e90217002d52203a90`) запустился скрыто на временном профиле с нулевой громкостью, позиция воспроизведения дошла до 10.9 с.

Локальный установщик: `MORA-Native-Preview-0.3.34-preview.1-Setup.exe`, 96 142 549 байт, SHA-256 `72983e3ad78e4f3c50c3056360404fbae768f98733799e900c8364edaef53225`. Не опубликован и не установлен.
