# Обновления MORA через GitHub Releases

Начиная с **0.3.14**, Windows-сборка использует `electron-updater` 6.8.9 и NSIS. Источник зафиксирован в конфигурации упаковщика: публичный репозиторий `Rizen1322/MORA`. Renderer не передаёт адреса обновлений, команды или пути к установщику.

## Поведение

- Проверка запускается через 15 секунд после старта, затем раз в 6 часов. В настройках есть ручная проверка.
- Автоматическая проверка не скачивает установщик. Пользователь видит доступную версию и размер, затем нажимает «Скачать обновление».
- Во время загрузки музыка продолжает играть. Доступны прогресс и отмена.
- Загрузка проверяется библиотекой по SHA-512 из `latest.yml`. Несовпадение суммы и ошибки подписи не переводят обновление в состояние готовности.
- Готовое обновление устанавливается только по кнопке и после нативного подтверждения. По умолчанию в диалоге выбран ответ «Позже».
- Обычный выход, закрытие в трей или наличие скачанного установщика сами по себе установку не запускают.
- Переустановка запускается тихо, после подтверждения; MORA перезапускается после завершения. Штатный обработчик `will-quit` завершает локальный backend перед выходом приложения.
- Установка запрещена во время переноса медиатеки. NSIS сохраняет профиль, `appId` и `deleteAppDataOnUninstall=false` не менялись.
- Предварительные версии и откат на меньшую версию отключены. Проверка и установка недоступны в режиме разработки.
- При сетевой ошибке, отмене или повреждённом файле текущая версия остаётся рабочей. Это не обещание автоматического восстановления после любого сбоя ОС во время установки.

Обновление yt-dlp в настройках остаётся отдельной функцией.

## Первый переход

**0.3.13 нужно обновить вручную до 0.3.14**: в старой программе нет кода автообновления. После этого следующие версии можно получать из приложения. Одной публикации `latest.yml` недостаточно, чтобы добавить функцию в уже установленную 0.3.13.

## Публикация

1. Увеличить desktop-версию и согласовать `package-lock.json`.
2. Прогнать тесты и typecheck, собрать `npm run desktop:package`.
3. Проверить `apps/desktop/dist/latest.yml`: его версия, имя, размер и SHA-512 должны соответствовать готовому EXE. `resources/app-update.yml` должен содержать `provider: github`, владельца `Rizen1322` и репозиторий `MORA`.
4. Создать тег и **черновик** GitHub Release. Загрузить `MORA-Setup-<версия>.exe`, его `.blockmap`, `latest.yml` и контрольную сумму `.sha256`.
5. Проверить загрузку всех файлов и только затем опубликовать обычный release как latest. Не включать предварительную версию в стабильный канал и не заменять файлы уже опубликованной версии.

Пример после создания тега:

```powershell
gh release create v0.3.14 apps/desktop/dist/MORA-Setup-0.3.14.exe apps/desktop/dist/MORA-Setup-0.3.14.exe.blockmap apps/desktop/dist/MORA-Setup-0.3.14.exe.sha256 apps/desktop/dist/latest.yml --verify-tag --draft --title 'MORA 0.3.14' --notes-file release-notes.md
gh release edit v0.3.14 --draft=false --latest
```

Команды запускаются в клоне `Rizen1322/MORA`. Упаковщик использует `--publish never`: обычная локальная сборка сама ничего не публикует. Нельзя публиковать метаданные раньше бинарных файлов.

## Доверие и ограничения

Сейчас установщик не подписан сертификатом Windows. Проверка целостности SHA-512 и HTTPS не заменяет подпись издателя: доверие распространяется на GitHub-репозиторий и его release-метаданные. Проверка подписи в библиотеке не отключена; при добавлении сертификата надо включить ожидаемого издателя в конфигурацию и отдельно проверить переход с неподписанных версий.

Отдельные тесты покрывают состояния, отмену, сетевые и checksum-ошибки, повторные команды и расписание. Интеграционный тест использует настоящий `NsisUpdater` с локальным сервером: старую версию не предлагает, повреждённый файл отвергает, изменённый кэш предыдущего запуска перепроверяет и скачивает заново. Тестовый EXE синтетический и никогда не исполняется.

Полная замена установленного приложения требует отдельной проверки Windows-установки; модульные тесты её не доказывают. Подписанная сборка, восстановление после отключения питания и антивирусные блокировки требуют собственного испытания.
