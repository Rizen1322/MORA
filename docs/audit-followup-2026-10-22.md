# Проверка приложенного аудита

Аудит прочитан как стороннее заключение, утверждения сверены с текущим кодом. Это не независимый полный аудит всех 21 пунктов.

## Что подтверждено и исправлено в этой работе

- **Подготовка голоса:** `/analysis/focus` раньше управлял только MIR и PCM; отделение вокала запрашивали позднее через prepare. Теперь есть ограниченный focus current/next + две локально доступные песни. Старые задания удаляются, кандидаты не скачивают источник и не запускают Whisper. Исчезнувший после постановки в очередь файл не вызывает скрытую загрузку и не оставляет вечную ошибку.
- **Порядок запуска:** готовый current мог синхронно запустить Whisper до постановки missing next. Теперь focus заполняет очередь целиком перед одним запуском. Необязательное распознавание уступает отсутствующему вокалу и не возвращает устаревшую работу в очередь.
- **SSE backpressure:** размер исходящего буфера раньше не проверялся. Теперь отстающий сокет отключается при >256 КиБ; здоровые клиенты и локальные слушатели продолжают получать события. После переподключения клиент заново получает библиотеку и обновляет подготовленный переход. Завершение Whisper имеет отдельное событие, не запускающее перепланирование аудио.
- **Открытие текста:** готовые локальные слова раньше ждали внешний поиск. Теперь они доступны сразу, без LRCLIB и без нового запуска модели. Суммарное время сетевых повторов и fallback-поиска ограничено 12 секундами. Ошибка сети не кэшируется как отсутствие текста.
- **JSON:** оба читателя локальных таймингов ограничены 2 МиБ. Слова вне активной строки не перерисовываются на каждом тике. При закрытии SSE-подписки очищается и отложенный reload библиотеки.

## Уточнения к утверждениям аудита

- Глобальный `setState({player})` действительно происходит часто, но **вся страница не обязана перерисовываться**: медиатека и другие компоненты подписаны через Zustand selectors на `tracks`, `order`, `loaded`. Компоненты, подписанные на весь player, остаются кандидатами на профилирование; очереди не глубококопируются React автоматически на каждый тик.
- `PublicMusic.covers` — карта **текущих запросов**, её запись удаляется в `finally`. Утечка «без eviction» для неё не подтверждается.
- Большинство перечисленных карт `StemService` удаляются при `prune()`. Нельзя утверждать, что они все гарантированно растут без очистки. Очередь спроса действительно требовала ограничения; это исправлено.
- `listDTO()` имеет N+1 по источникам, а одиночный track endpoint действительно строит весь список. Это остаётся отдельной задачей. На текущем dev-профиле 277 записей два GET с разбором JSON заняли 68 и 37 мс; эти замеры не подтверждают секунды на нынешней библиотеке и не отменяют проблему больших библиотек.
- `convert()` действительно буферизует старый f32 при переходе в s16. Новые стемы считаются последовательно; утверждение о множестве параллельных таких преобразований не подтверждено. Потоковая конвертация остаётся отдельной оптимизацией.
- Карта цветов без лимита, дальнейшая инкрементальная загрузка библиотеки, desktop log rotation/recovery, импорты и остальные накопления требуют отдельной проверки. Здесь они не объявляются исправленными.

## Измерения именно установленного приложения

В `%LOCALAPPDATA%/MORA/data` найдено 38 готовых stem metadata. Последние десять: CPU, длительности песен 107,6–179,0 с, отделение 14,23–28,44 с, медиана 21,125 с. Активного процесса Python во время проверки не было. Это подтверждает смысл подготовки вперёд; ускорение самой модели не измерялось.

В установленном профиле не было `lyrics.json`, а в bundled runtime не найден пакет Whisper. Dev-профиль с системным CUDA Python отличается: 33 готовых партии, почти все с таймингами слов. Нельзя переносить выводы о CUDA или скорости распознавания из dev на установленное приложение. Новые веса или зависимости не загружались. Пословная подсветка работает с уже доступными валидированными таймингами; без них остаётся построчный LRC.
