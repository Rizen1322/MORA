# iOS: единая ветка и переход на Swift

## Ветки и следующий релиз

Линия интеграции — `unified/mora-2026-11-10`: iOS-изменения объединены с актуальным кодом ПК и общих модулей с сохранением обеих историй. Дальнейшие нативные экраны проходят проверку на этой общей базе.

`main` остаётся линией опубликованного проекта; переносить туда отдельно старую iOS-ветку нельзя: это снова разойдётся с общим кодом ПК. Следующее объединение с `main` следует делать из проверенной общей линии.

Следующая версия — **1.0.41 (42)** для приложения и виджета. Она задана в `apps/mobile/package.json`, lockfile и Xcode project. `ios-mac.sh` и `verify-ipa.cjs` получают версию из package.json; build остаётся patch + 1. Исторические документы и IPA 1.0.40 (41) не переименовываются.

## Этап 1: прямые данные и файлы

- `NativeLibraryStore` открывает тот же `Application Support/server/data/automix.sqlite` только для чтения. Схему и записи продолжает обслуживать существующий сервер в JavaScriptCore.
- Медиатека, реакции, плейлисты с повторяющимися entries и история читаются одной транзакцией SQLite. WAL сохраняет согласованность снимка. `PRAGMA data_version` позволяет пропускать чтение неизменённой базы.
- Swift обновляет данные в foreground раз в секунду и при сообщениях моста. Чтение выполняется на отдельной последовательной очереди. Технические треки вне сохранённой коллекции остаются доступны истории и плейлистам.
- После ответа `libraryInSwift` веб перестаёт формировать и передавать массивы медиатеки и плейлистов. Старый нативный клиент и OPFS fallback сохраняют прежний протокол.
- Содержимое списка плейлистов, плейлиста и истории формируется в Swift. Создание, редактирование и экспорт плейлистов, очистка истории и реакции теперь обращаются из Swift прямо к JSC API; маршрутизация и воспроизведение также ещё зависят от страницы.
- Для локального или закэшированного файла сервер передаёт виртуальный `serverPath`. Swift проверяет путь под корнем общей файловой системы, тип, размер и выход через symlink; существующий native lease получает ссылку на файл. Байты трека не проходят через страницу/base64. Binding выбирает аудио подменённой записи с сохранением названия и реакции исходного трека.
- Если файл недоступен напрямую, сохраняется прежняя передача кусками. OPFS fallback остаётся до успешного переноса старых данных. Ограничения lease: 128 МиБ на файл, 512 МиБ суммарно.

Это перенос чтения и части представления данных, а не перенос всех операций записи на Swift. SQLite-схема не меняется; миграция не удаляет исходную OPFS-медиатеку.

## Этап 2: настройки и загрузки

`/settings` и `/downloads` после переноса базы открывают самостоятельные SwiftUI-экраны `NativeSettingsView` и `NativeDownloadsView`. Они больше не запрашивают `page` и не вызывают действия через `window.moraNativeUi`. До завершения OPFS-миграции сохраняется прежний экран.

- Настройки читаются непосредственно из API сервера в JavaScriptCore; PUT содержит только изменённый ключ. Сохранены обычные и расширенные параметры AutoMix, звук и другие ссылки, проверка файлов, очистка PCM-кэша, экспорт медиатеки/плейлистов, просмотр и восстановление JSON-копии, экспорт ZIP диагностики. При ошибке сохранения форма возвращается к последнему подтверждённому состоянию.
- Загрузки показывают обе очереди: серверную и системную фоновую. Есть прогресс, пауза, повтор со свежим адресом, отмена с подтверждением, скачивание любимого, скачанные треки и собственные файлы, предел и очистка кэша. Wi-Fi настраивается в одном месте — `/settings` — и применяется к системным фоновым задачам.
- Swift обращается к существующим API через `NativeServer.request`. Отрицательные ID отделяют эти запросы от запросов страницы; повторное подключение WebView их не отменяет. Есть таймаут, отмена задачи, ограничение JSON-ответа 16 МиБ и передача ошибок API в интерфейс.
- После сохранения настроек и восстановления полной копии сервер публикует событие `settings`. Оставшийся веб-контроллер перечитывает значения и применяет громкость, AutoMix и параметры звука без повторной записи. При подключении/возобновлении канала событий настройки перечитываются снова; устаревший ответ не отменяет редактирование звука.

Загрузка, сохранение и отображение этих двух экранов больше не зависят от работающей страницы. Навигация, воспроизведение треков из списка и подбор волны пока остаются за прежним контроллером — это этап 4.

## Этап 2: звук и резервные копии

`/sound` и `/backups` открывают самостоятельные `NativeSoundView` и `NativeBackupsView` после переноса базы. Звук сохраняет 10 полос, диапазон ±12 дБ, шаг 0,5 дБ и встроенные/пользовательские пресеты. Изменение полосы применяется к свежим данным сервера; частичный PUT `sound.tone` теперь объединяется с сохранёнными полями, сохраняя баланс, mono, реверберацию, скорость, высоту тона и пользовательские пресеты. При неопределённом результате записи экран перечитывает сервер, не записывая старое состояние в качестве отката.

Список копий читается прямо из локальной/iCloud папки. Выбор фиксирует содержимое для предварительного просмотра, восстановления с подтверждением и экспорта. Недоступность iCloud не скрывает локальные копии. Общий файловый helper используется и в настройках: чтение ограничено 16 МиБ до декодирования, символьные ссылки за пределы папки автоматических копий отвергаются, экспорт создаёт отдельный временный файл. Успешное восстановление отделено от ошибки последующего обновления настроек, чтобы интерфейс не предлагал повторить уже выполненную операцию.

Автоматическая копия на сворачивании и по таймеру теперь получает JSON прямо от JSC-сервера; работа страницы для сбора данных не требуется. Проверка дубликата также использует ограниченное чтение предыдущей копии. Старая OPFS-ветка продолжает использовать прежний мост до завершения миграции.

## Этап 2: действия плейлистов, истории и реакции

После переноса базы Swift напрямую выполняет создание, переименование и удаление плейлиста, добавление треков с сохранением повторов, удаление конкретной записи по entry ID, перестановку, экспорт JSON и очистку истории. Поддерживаемая операция при ошибке не повторяется через страницу; после записи Swift перечитывает базу, не откатывая подтверждённое изменение из-за ошибки обновления экрана.

Реакции используют прежний сохраняемый outbox и прямой `POST /api/tracks/:id/reaction`. Подтверждение старого запроса не стирает более новое переключение; после сбоя неподтверждённая реакция остаётся для повторной отправки. Общая очередь используется плеером, Siri и CarPlay; в фоне сохраняется намерение пользователя, отправка выполняется при активном приложении. Массовый лайк меняет только нейтральные записи, не перезаписывает дизлайки и не дублирует одинаковые ID.

Пропуск после подтверждённого дизлайка пока остаётся командой веб-контроллера: перед `nextTrack('dislike')` он проверяет, что играет тот же трек и контекст волны. Это защита от пропуска уже сменившегося трека, а не завершённый этап 4. Воспроизведение, загрузки из меню трека, метаданные и другие неподдерживаемые действия ещё используют страницу. Для OPFS сохраняется прежний путь.

## Проверка объединения

Реальная сборка обнаружила потерянный в общей ветке вызов `startNativeUi()` из production entry. Без него Swift-оболочка не подключалась, а код офлайн-волны вырезался из бандла. Вызов восстановлен, добавлен runtime-тест entry до React render; проверки IPA не ослаблялись. Симуляторный тест теперь запускается до подключения моста и пишет ошибку запуска даже при отсутствующей оболочке.

Восстановлены кнопка возврата из веб-режима в нативный интерфейс и выбор Swift-плеера из телефонного store. Готовый хвост iOS-волны передаётся нативному host без ожидания медленного пополнения; недоступные записи удаляются по `entryId` с сохранением текущей записи, истории и параллельных изменений очереди. Первый запрос Яндекс-волны на iOS запрашивает один трек. Desktop-путь ожидания пополнения сохранён.

Остаются ограничения старого контроллера: общего 60-секундного срока запуска волны пока нет (запрос Яндекса может ждать до 180 секунд), а веб-визуализация при нативном звуке ещё не получает native levels. Это не завершённый этап 4; Swift-плеер и его уровни остаются отдельным нативным путём.

## Проверки

Windows: `npm run typecheck`, `npm run mobile:build`, Vitest для server/web/mobile. Полный набор аудиотестов требует FFmpeg/FFprobe и demo fixtures.

При объединении устранён импорт desktop Rust HTTP helper в мобильный бандл: mobile replacement использует host fetch и существующую загрузку. В Яндексе сохранены обе линии: асинхронные обложки ПК, metadata-only импорт iPhone, порядок лайков по датам и готовые метаданные из rotor. Fixture phrase-recipes теперь предоставляет доступный аудиоисточник, поскольку iOS исключает недоступные записи из handoff.

macOS: workflow `.github/workflows/ios.yml` компилирует отдельный `native-library` self-check (WAL, незакоммиченные изменения, реакции, binding, повторения плейлистов, история и ошибки схемы), существующий `native-http` self-check проверяет пути и symlink, затем собирает приложение и виджет. Swift, IPA и Simulator нельзя подтвердить запуском TypeScript-тестов на Windows.

Для этапа 2 добавлены Foundation self-checks `native-settings` и `native-downloads`. `native-server` проверяет прямые GET/PUT, ошибки HTTP/JSON, таймаут, отмену и запрос во время переподключения страницы. Симуляторный `--native-ui-check` запрещает получение описания `/settings` и `/downloads` из страницы, проверяет синхронизацию AutoMix после нативной записи и снимает оба экрана. Прогресс загрузки в этом сценарии — явно диагностическая строка в памяти Swift, без сети и без записи в очередь на диске.

На Windows проходят typecheck, mobile:build и целевые тесты bootstrap, передачи очереди, offline wave, настроек и резервных копий. Новые Swift-файлы включены в app target; Xcode project разобран парсером `xcode`.
