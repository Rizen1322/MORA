# Непрерывная Яндекс-волна

20 октября 2026. Исправлен общий механизм пополнения волны и путь Yandex Rotor → подготовка полного аудио → очередь → анализ → ближайший переход.

## Причины задержек

Раньше doPrepare ждал topUpWave перед планированием даже уже доступной пары. Пополнение начиналось при остатке меньше двух треков. Сервер готовил два доступных трека за запрос, браузер не передавал полученные Yandex IDs в Rotor queue. Последний batchId хранился глобально и подменял атрибуцию старых рекомендаций. Ошибки Яндекса могли незаметно приводить к добавлению локальных рекомендаций.

## Новое поведение

- Быстрый старт: сервер по умолчанию готовит два доступных трека, не весь ответ каталога. Старт Яндекс-волны допускает один готовый трек и не требует добавлять локальные рекомендации.
- Скользящий резерв: пополнение при остатке менее четырёх треков либо менее восьми минут при количестве меньше шести. Цель запроса — приблизиться к шести; максимум восемь будущих entries как дополнительная защита. Это ограниченный резерв, а не скачивание всей выдачи.
- До трёх запросов в одном цикле; один запрос готовит не больше четырёх новых треков, одновременно выполняются максимум два импорта. Неудачных попыток не больше count+1. Уже готовые треки учитываются до начала загрузок.
- Одинаковое аудио под разными ID может сохраняться одновременно. Ошибка публикации файла на Windows принимается только после проверки, что другой импорт уже опубликовал содержимое с тем же SHA-256; посторонний файл не считается успешной загрузкой.
- Ближайшая доступная пара планируется независимо от загрузки рекомендаций. Если ближайшего трека вообще нет, подготовка ждёт пополнение.
- На старте, при смене трека и во время воспроизведения проверяется резерв. Одновременные вызовы объединяются в один promise; пауза не блокируется фоновой загрузкой.
- Браузер отправляет до 200 полученных Yandex IDs в POST /api/providers/yandex/wave. Backend передаёт их Rotor, исключает их также локально, объединяет ID разных альбомов по базовому track ID и убирает повторы внутри ответа. Учитываются доступные локальные дизлайки; клиент повторно проверяет актуальную очередь/реакции после HTTP.
- Новые готовые кандидаты заранее получают приоритет анализа. PCM и план непосредственно следующего трека идут через существующий engine/prepare path.
- При unknownSession открывается новая сессия с прежними исключениями.
- При ошибках/пустых ответах повтор через 10–60 секунд с увеличением интервала; успешный цикл ограничен минимальной паузой 5 секунд. Фоновый повтор на паузе не продолжается. Если закончился последний трек, плеер остаётся в ожидании и автоматически начинает продолжение после успешной загрузки; ручная пауза отменяет такое автоматическое продолжение.
- Ручной Next при пустом остатке тоже пытается пополнить волну. Смена контекста/новый запуск отменяют применимость старого результата. Обычная смена текущего трека внутри той же волны не отбрасывает полезную загрузку.
- Если последний трек не загрузился, волна также переходит к ожиданию резерва и продолжает после успешной подготовки следующего.
- Нет незаметной подмены Яндекс-волны локальной подборкой при сетевой ошибке. В интерфейсе видны загрузка и ожидание повторной попытки.
- Длинная очередь хранит около 120 прошлых entries плюс резерв; обрезка не производится во время активного blend. Оригиналы и пользовательская медиатека не удаляются.

## Обратная связь и восстановление

Каждый новый Yandex entry сохраняет yandexSessionId/yandexBatchId. trackStarted/skip/trackFinished получают атрибуцию именно этого entry, а не последней загруженной пачки. Финальный feedback не зависит от успешной записи локальной истории и не отправляется дважды. Skip/dislike/error не выдаются за полное прослушивание. Длительность feedback накапливается по времени активного воспроизведения, а не по положению после seek.

Метаданные автоматически сохраняются существующим queue API. После восстановления сессия берётся из entries; истёкшая восстанавливается через unknownSession. У старых сохранённых entries без атрибуции feedback не отправляется с выдуманным новым batchId. Источник на странице синхронизируется с восстановленным контекстом.

Не реализована долговечная повторная доставка feedback при сетевой ошибке: её нельзя путать с повторными попытками загрузки рекомендаций, которые реализованы. Настройки энергии/характера сохраняют прежнюю семантику приложения; серверные seeds Яндекса в этой задаче не перенастраивались.
