# SoundCloud: ускорение поиска, 22 октября 2026

Вместо запуска Python/yt-dlp для каждого нового запроса появился metadata-only путь `apps/server/src/public/soundcloud.ts`. Он использует публичный `search/tracks` SoundCloud. Аудио по-прежнему получает существующий resolver и воспроизводит один AutoMix engine. Аккаунт, cookies и пользовательские токены не нужны.

Идентификатор текущего публичного web-клиента обнаруживается в официальных JS assets сайта и хранится только в памяти 30 минут. Он не зашит в код. Это тот же принцип bootstrap, который использует [официальный SoundCloud extractor yt-dlp](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/soundcloud.py#L114-L150). Прямой поиск не запрашивает аудио/CDN и не создаёт записи медиатеки.

## Ограничения и проверки

- Общий бюджет прямого пути 4 с, включая bootstrap; при неудаче provider использует существующий yt-dlp fallback. Неудачный прямой путь пропускается следующие 30 с, чтобы каждый запрос не платил одинаковый таймаут.
- HTML ограничен 1 МиБ, не более трёх официальных assets `a-v2.sndcdn.com/assets/*.js` по 4 МиБ, API 2 МиБ; ограничение проверяется при чтении потока. Redirect запрещён, произвольные ссылки из HTML не запрашиваются.
- Отмена до или во время discovery останавливает fetch и не включает cooldown. После 401/403 текущий client ID сбрасывается. Private, BLOCK, SNIP и явно нестримимые записи не выдаются как полные треки.
- Parser сохраняет только валидные ID, длительности и разрешённые обложки sndcdn, удаляет повторы; отсутствие artwork может заменяться avatar источника.
- Пять unit tests прямого поиска проверяют bootstrap/cache, metadata/cover, validation, отмену, deadline/cooldown, oversized stream. Интеграционный fallback проверяется отдельно provider tests.

## Review прогрева metadata

В `public-warmup.test.ts` добавлено 8 targeted tests: четыре записи / TTL 45 с, один speculative subprocess даже при двух вызовах в одном tick, отмена и retry, отказ от прогрева при единственном playback slot, `--load-info-json` reuse и правильный network target, отказ от почти истёкшего URL, retry только до публикации аудио, отсутствие повторной записи partial audio/после отмены.

Review нашёл race: счётчик speculative jobs увеличивался в microtask после синхронной проверки, поэтому два URL могли занять два процесса. Основной агент перенёс reservation перед await; regression проходит. Проверки `soundcloud-search.test.ts` и `public-warmup.test.ts`: **13 tests passed**. `tsc -p apps/server` также прошёл.

Голосовое качество, playback startup warm/cold и сеть друга этим поисковым smoke не проверялись. Публичная форма SoundCloud не является стабильным API-контрактом: её изменение должно возвращать пользователя к независимому yt-dlp пути, а не к ложным пустым результатам.
