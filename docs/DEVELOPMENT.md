# Разработка и выпуск MORA

## Окружение

- Windows x64 для упаковки и проверки релиза.
- Node.js ≥ 22.13; CI использует Node.js 24.
- FFmpeg/ffprobe для анализа и аудиотестов.

```powershell
npm ci
node apps/desktop/scripts/fetch-ffmpeg.mjs
node apps/desktop/scripts/fetch-ytdlp.mjs
```

Скрипты загрузки фиксируют версии и проверяют контрольные суммы. Vendor-файлы сохраняются локально в `apps/desktop/vendor/`, не в Git.

## Запуск

```powershell
npm run desktop:dev
```

Для отдельного веб-режима нужны доступные FFmpeg/ffprobe. Скопируйте `.env.example` в `.env`, при необходимости укажите пути и выполните `npm run dev`. Не направляйте тестовые инструменты на основной пользовательский профиль.

## Проверки

```powershell
$env:FFMPEG_PATH = "$PWD/apps/desktop/vendor/ffmpeg/ffmpeg.exe"
$env:FFPROBE_PATH = "$PWD/apps/desktop/vendor/ffmpeg/ffprobe.exe"
$env:PATH = "$PWD/apps/desktop/vendor/ffmpeg;$env:PATH"
npm run demo:tracks
npm run typecheck
npm test
npm run build
```

`demo:tracks` создаёт синтетические записи и намеренно повреждённые файлы для интеграционных тестов. Они генерируются локально и не содержат пользовательскую музыку. Без них часть серверных интеграционных тестов пропускается.

CI выполняет эти проверки на Windows. Он не публикует релизы, не подписывает установщики и не заменяет проверку живого приложения и прослушивание переходов.

В CI лимит ожидания одного теста — 180 секунд: длинная офлайн-симуляция восьми треков может не уложиться в локальный лимит 60 секунд на общем runner. Проверки качества внутри тестов при этом не ослабляются.

## Упаковка

```powershell
npm run desktop:package
```

Результат: `apps/desktop/dist/MORA-Setup-<версия>.exe` и `apps/desktop/dist/win-unpacked/`. Только папка приложения: `npm run package:dir -w @automix/desktop`.

## Релиз

1. Зафиксировать исходники, версию `apps/desktop/package.json` и согласованный lockfile.
2. Прогнать проверки и собрать приложение из этого снимка.
3. Проверить запуск с отдельным пустым профилем, комплект инструментов и штатное завершение. Сетевые проверки и прослушивание описывать отдельно.
4. Посчитать SHA-256 установщика, проверить состав публикации и выпустить GitHub Release с тегом `v<версия>`.
5. Приложить установщик, файл `.sha256`, `.blockmap` и **`latest.yml`**. Проверить версию и SHA-512 в метаданных, затем опубликовать release. Неполный набор файлов оставлять черновиком.

Начиная с 0.3.14 используется `electron-updater`; подробности и команды публикации — в [AUTO_UPDATE.md](AUTO_UPDATE.md). Обычная упаковка работает с `--publish never` и сама файлы на GitHub не отправляет. Автоматический откат после любого сбоя установки не реализован; сетевые и checksum-ошибки до запуска установщика оставляют текущую версию рабочей.

## Что не публикуется

`.env`, профили, базы SQLite, скачанная музыка, токены, кэши PCM/стемов, локальные модели, vendor и выходные каталоги сборки исключены из Git. Мобильная ветка разработки в этот desktop-снимок не включена.
