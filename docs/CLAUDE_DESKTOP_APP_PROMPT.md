# Промпт для Claude: настольный AutoMix

Скопируй текст ниже в Claude, работающий в этом репозитории. Он должен реализовать приложение, а не ограничиться планом.

---

Ты продолжаешь существующий AutoMix в `E:\вин\ПРОЕКТЫ\music`. Сделай полноценное Windows-приложение из текущего проекта. Сохрани фирменный дизайн, музыку, очередь, аккаунт Яндекса и работающий AutoMix. Приложение должно ощущаться самостоятельным музыкальным инструментом: удобным, быстрым и красивым, с нативным поведением окна. Пользователь не должен запускать терминал, Node, Python или отдельный сервер.

## Сначала изучи текущее состояние

Прочитай README, package.json, актуальные инструкции репозитория, `docs/design-notes.md`, имеющиеся `DESIGN*.md`, локальные skills в `skill/`. Обязательно прочитай:

- `docs/audit-automix-desktop.md`
- `docs/audit-audio-desktop.md`
- `docs/audit-player-desktop.md`
- `docs/yandex-wave-continuous.md`
- `docs/desktop-preparation-2026-10-20.md`
- `docs/iphone-local-offline-plan.md`
- актуальные документы о vocal pipeline, PCM headroom и v7.

Фактический код имеет приоритет над старыми handoff. Здесь параллельно работали Claude и Codex, большинство исходников могут быть untracked. Не делай reset/clean, не перезаписывай чужие изменения. `.env`, data-dev и база — реальные данные пользователя; не выводи токены и не очищай медиатеку. Проверки записи делай на отдельной временной базе. Имена skill-пакетов из переписки не означают, что они установлены: сначала проверь наличие файлов.

Архитектура сейчас: React/Zustand/Vite в apps/web, локальный Node/Fastify backend в apps/server, DSP/планировщик в packages/core, AudioWorklet для вывода, FFmpeg/FFprobe и Python pipeline для тяжёлого анализа/stems. Уточни текущие зависимости и версии по коду. Не переписывай DSP ради desktop-оболочки.

## Выбор оболочки и упаковка

По умолчанию выбери Electron для первого Windows-релиза: можно сохранить текущий React и Node backend. Если в проекте уже появилась качественная desktop-реализация — продолжи её. Tauri рассматривай только после проверки совместимости Node/SQLite/Python/FFmpeg и оценки реальной стоимости переноса; небольшой размер оболочки сам по себе не решает размер ML-моделей и расход памяти.

Создай apps/desktop с понятными dev/build/package командами. Собери работоспособный installer или portable output для локальной проверки. Проверь именно packaged build на машине без глобального Node/Python/FFmpeg, а не только dev-окно. Не скачивай гигабайты моделей на старте: базовое прослушивание работает сразу, расширенный анализ устанавливается отдельным понятным пакетом. Учитывай лицензии распространяемых бинарников и моделей. Если подпись сертификатом недоступна, явно зафиксируй это как ограничение сборки, не утверждай, что релиз подписан.

Backend — внутренний компонент приложения. Для первого этапа можно сохранить HTTP API на 127.0.0.1 со случайным свободным портом, случайным launch token и проверкой запросов/Origin, без доступа из LAN. Не вшивай постоянный 4730 и не рассчитывай на открытый браузер. Renderer получает адрес через узкий preload bridge. Проверь AudioWorklet, range PCM, SSE и загрузку обложек в packaged origin: подстановка одного base URL недостаточна. Если выбираешь custom app protocol/IPC, докажи поддержку нужных audio/network API интеграционными тестами.

Не допускай двух backend-процессов и двух AudioContext при повторном запуске. Реализуй single-instance lock, корректный shutdown, отмену работ, восстановление после падения backend без бесконечного respawn. SQLite/загрузки не должны повреждаться при закрытии окна. Пользовательские файлы живут в userData/выбранной папке, а не внутри установленного приложения. Для существующей data-dev предложи безопасный импорт с резервной копией и атомарной миграцией; не переноси её молча.

## Окно и ощущение приложения

Начальный размер примерно 1280×820 DIP, минимум 960×680 DIP. Это стартовая геометрия, окно обязательно свободно растягивается, разворачивается и работает со Snap Layouts. На маленьком экране размер ограничивается доступной рабочей областью. Сохраняй bounds/maximized, исправляй координаты после отключения монитора, тестируй DPI125/150/200% и смену мониторов.

Верхняя панель интегрирована в дизайн: drag regions, двойной клик для maximize, нативные minimize/maximize/close через titleBarOverlay или проверенный эквивалент. Кнопки, поиск и поля ввода исключены из draggable region. Никаких браузерных адресных строк, искусственных полей с URL и бессмысленного меню File/Edit по умолчанию. Клавиатура, focus ring, контекстное меню, drag-and-drop папок, системный выбор файлов работают как в приложении.

Сохрани хвойную тёмную палитру, Onest/Unbounded, мягкий зелёный акцент; янтарный оставь для AutoMix. Используй актуальную главную с центральной «Моей волной», компактными вторичными элементами, обновлённую медиатеку/любимое/плейлисты и нижний player dock. Не делай маркетинговый лендинг внутри окна. Не показывай пользователю технические термины IPC/PCM/backend вместо нормальных состояний «Готовим трек», «Нет подключения», «Продолжить».

Движение: короткая тактильная реакция120–200ms, смена панелей200–350ms, спокойная пространственная 3D-волна. На resize ничего не дёргается, списки не перестраиваются через layout-анимацию тысяч строк. Не добавляй одновременно GSAP/R3F/Babylon/Rive без конкретной необходимости. Используй существующий Three.js, ленивую загрузку и CSS/WAAPI. При reduced motion — статичный красивый объект. Скрытое/свёрнутое окно прекращает декоративный render loop и анализатор визуализации, но продолжает звук.

## Системная интеграция

Media keys/системный transport вызывают единственный controller: Play/Pause/Next/Previous/Seek, обложка и Now Playing согласованы с текущей очередью. Поведение закрытия понятно: настройка «Закрывать в трей», настоящее «Выйти» в меню трея. После явной паузы музыка самопроизвольно не включается. Предусмотри sleep/wake, отключение наушников, смену audio device, Bluetooth, закрытие/перезапуск UI во время музыки. Если текущая архитектура уничтожает AudioWorklet с renderer, честно реши жизненный цикл: скрывай основное окно или выдели устойчивый audio host; не создавай второй транспорт для красивой оболочки.

Внешние ссылки открываются системным браузером только по действию пользователя. Renderer sandbox/contextIsolation включены, nodeIntegration выключен; preload предоставляет минимальные операции с валидацией параметров. Не предоставляй произвольные fs/exec/IPC каналы. Секреты храни через доступные средства ОС; не делай токен доступным странице или логам. Не загружай удалённый HTML с привилегиями приложения.

## Оптимизация, которую нужно измерить

Сначала baseline, затем изменения. Замерь холодный/тёплый запуск, первый звук с готовым треком, RSS каждого процесса в idle/playing/analysis, CPU/GPU свёрнутого окна, количество worklet underruns и размеры дисковых кэшей. Укажи железо и условия. Не подменяй измерения обещаниями «60fps» и «нулевой CPU».

Main/renderer не выполняют FFmpeg, separation, большие обходы файлов и синхронную работу SQLite. Тяжёлые задачи — worker/utility/дочерние процессы с лимитами, cancel, таймаутами и приоритетом текущей/следующей пары. Audio render callback не должен делать I/O, сетевые запросы, логирование или большие аллокации. Не включай глобально backgroundThrottling:false ради декоративной анимации: сначала проверь жизненный цикл audio host.

Сохрани bounded PCM windows, generation/ACK contracts, f32 headroom и single-WSOLA stem path. Не возвращай PCM в int16 до суммирования. Кэши originals/analysis/PCM/stems разделены; размер, LRU, pinned current/next/offline файлы, атомарная публикация и восстановление после незавершённой загрузки. Не удаляй офлайн-треки как обычный cache. Пакетная обработка библиотеки не должна мешать текущему переходу.

Яндекс-волна уже пополняется заранее небольшими партиями, имеет singleflight/backoff/exclusions и per-entry session/batch feedback. Сохрани это. Настройки провайдера получаются из GET /api/providers/yandex/wave/settings, сохраняются в wave.yandexSeeds, затем controller.refreshYandexWave() сохраняет current/prepared pair и обновляет дальнейшие рекомендации. Не заменяй настоящие настройки локальными «энергия/разнообразие».

## Проверка и критерии готовности

Используй npm run typecheck, npm run build и целевые тесты; перед передачей запусти полный доступный suite. Отдельно проверь packaged app: запуск без dev server, повторный запуск, импорт Unicode-пути, восстановление очереди, длительное воспроизведение и переход, перемотка назад, Pause во время загрузки, сеть пропала/вернулась, работа в трее, сон/пробуждение и выход без оставшихся процессов. Протестируй минимальное, обычное и развёрнутое окно, разные DPI; сохрани скриншоты и метрики.

Не утверждай, что качество звука проверено прослушиванием, если были только unit-тесты. Не меняй музыкальные алгоритмы и пороги на слух без пары исходных/итоговых примеров и воспроизводимого дефекта. Исправления аудита уже внесены — прочитай их и не откатывай.

Результат: установленное или portable Windows-приложение, команды сборки, краткая архитектура, скриншоты, фактические результаты проверки, список оставшихся ограничений и инструкции для следующего разработчика. Продолжай до рабочего результата; не заканчивай на плане.
