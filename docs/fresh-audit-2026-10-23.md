# Свежий аудит MORA / AutoMix — 23 октября 2026

Аудит со свежего взгляда: ошибки, оптимизация, идеи для переходов. Код продукта не менялся. Базы `data-dev/automix.sqlite` и `%LOCALAPPDATA%\MORA\data\automix.sqlite` открывались только на чтение. Сервер на порту 4730 не трогался.

Скрипты замеров лежат в `tools/.cache/fresh-audit/`:
- `bench.ts` — время планирования;
- `render-bench.ts` — рендер-проверка и выход окна за конец файла;
- `sqljs-export.cjs` — экспорт базы в sql.js, в памяти.

Профили CPU лежат в `prof1/`, `prof2/` и `prof3/`.

Перед аудитом прочитаны: README, `dj-automix.md`, `stemless-automix-implementation-2026-10-22.md`, `mobile-stemless-automix-research-2026-10-22.md`, `apps/mobile/README.md`, `automix-ideas-2026-10-22.md`, `repo-performance-audit-2026-10-22.md`, `audit-fixes-2026-10-22.md`, `pc-optimization-2026-10-22.md`. Уже сделанное и отвергнутое здесь не повторяется. Так, стем-обмен баса отклонён 22.10, мост темпа и drop между грувами удалены, эхо поверх чужого ритма запрещено. Не повторяются и нейросетевые P11/P12 и Beat This!.

## Главное

1. **Рендер-проверка P10 почти не участвует в живом воспроизведении.** Клиент запрашивает план раньше, чем начинает декодировать B. Поэтому первый план всегда помечается «PCM не готов». Повторный запрос плана приходит только при новом анализе (раздел 1, О1).
2. **У 13–20 % пар P10 отключена навсегда.** Окно рендера A выходит за конец файла, и `readSpan` его отвергает. Эту ошибку исправляет одна строка (О2).
3. **Короткие сведения — главная причина «резко».** Из 15 оценённых переходов короче 8 с хороший только один. Вечером 22.10 (`v11-dj-8`) 7 из 12 сведений по битам длились 4 такта, 6,3–9,9 с. Причины: альтернатива `short-phrase` и предпочтение 4 тактов при конфликте тональностей (П1, П2).
4. **iPhone перезаписывает всю базу примерно раз в 5 секунд во время игры.** Клиент сохраняет позицию в очереди, а sql.js после каждой записи выгружает полный образ базы в OPFS (Опт1).
5. **93 % базы `data-dev` — анализы старых версий** (152 из 163 МБ). Их никто не удаляет (Опт2).
6. **Половина времени планировщика уходит на `Math.pow` в `powerLevel`** (47–61 % по профилю). Кэш линейной мощности даёт побитово тот же результат (Опт3).

## 1. Ошибки

Порядок — по пользе.

### О1. P10 не проверяет первый план реальной пары, а повторной проверки обычно нет

- **Место:**
  - `apps/web/src/audio/controller.ts:1301`: `api.plan` вызывается до `loadSlot`;
  - `controller.ts:1313` → `324`: `api.prepare(next)` открывает декодирование B только здесь;
  - `apps/server/src/routes/playback.ts:157–163`: `readSpan` не начинает новое декодирование;
  - `apps/server/src/automix.ts:110–116`: план без PCM кэшируется с `renderCheck.skipped`;
  - `automix.ts:99–102`: перепроверка идёт только при следующем запросе.
- **Что не так.** Клиент запрашивает план для пары до того, как сервер начал декодировать B. Если PCM трека B на этой частоте ещё нет в дисковом кэше, `pcm.status(key, rate)` у B пуст. Тогда `readSpan` возвращает `null`, и в кэш ложится непроверенный план. Следующий `api.plan` для этой пары делают только `onAnalysisDone` и `onVocalsChanged` (`controller.ts:1439–1481`), то есть при новом анализе или стеме. При обычном прослушивании плейлиста повторного запроса нет: P10 срабатывает только для треков, чей PCM уже лежит в кэше от прошлых прослушиваний.
- **Доказательство.** Чтение кода, путь вызовов выше. В `transition_log` обеих баз нет ни одной записи `am-planner-v12-fullmix-*`, поэтому живого подтверждения нет. Последняя запись `data-dev` от 21.10, установленного профиля — `v11-dj-8`.
- **Польза.** P10 начнёт работать там, для чего её делали: в реальной очереди, особенно на iPhone, где голос всегда неизвестен.
- **Как исправить, два варианта:**
  - (а) В `doPrepare` запускать `api.prepare(entry.trackId, sr, 'next')` параллельно с `api.plan`. `readSpan` уже ждёт до 1,5 с, а ffmpeg на ПК декодирует 80 с за доли секунды.
  - (б) Надёжнее и для iPhone: после того как пара подготовлена, если у плана есть `debug.renderCheck.skipped`, один раз запросить план повторно тем же путём, что в `onAnalysisDone`, при условии `startsIn ≥ 4 с`.
- **Риск.** Средний: изменятся реально звучащие планы пар без стемов. Вариант (б) добавляет один HTTP-запрос и рендер 2–5 финалистов на пару (Опт5).
- **Цена.** 10–20 строк в `controller.ts`.

### О2. `readSpan` отвергает окно, которое выходит за конец файла A

- **Место:** `apps/server/src/routes/playback.ts:167`: `if (n < frames * 0.98) return null;`.
- **Что не так.** `finalistSpans` (`packages/core/src/engine/render-check.ts:22`) берёт окно A до `aExit + длина + 1 с`. Если A звучит почти до последнего сэмпла, окно на 0,3–1 с длиннее файла. `pcm.read` честно отдаёт меньше кадров (`pcmCache.ts:227`), и проверка на 98 % отвергает их. Пара получает `pcm-not-ready`. Каждый следующий запрос заново планирует всех финалистов и снова упирается в ту же проверку.
- **Доказательство, замер `render-bench.ts`.** На 300 детерминированных парах без стемов получилось 39–59 случаев отказа, то есть 13–20 % пар с несколькими финалистами. На треках `am-analyzer-11` — 39 из 298, на `am-analyzer-12` — 59 из 297. Окно выходит за конец A в 65 и 93 парах.
- **Однострочная правка** (не внесена: она меняет звучание этих пар, поэтому решение за пользователем):
  ```ts
  if (n < Math.min(frames, r.totalFrames - start) * 0.98) return null;
  ```
  Тогда дека A в рендере заканчивается там же, где реальный файл. Когда декодирование завершено, `r.totalFrames` точен. Пока оно идёт, это оценка по длительности, и ошибка ведёт в безопасную сторону: окно отвергается, как сейчас.
- **Польза.** P10 включается ещё для 13–20 % пар.
- **Риск.** Низкий.
- **Цена.** 1 строка и тест.

### О3. Анализы старых версий никогда не удаляются

- **Место:** `apps/server/src/analysis.ts:221–225`: строка добавляется по ключу `(content_hash, version)`. Удаление есть только для одного трека (`analysis.ts:120`, `202`).
- **Доказательство, `data-dev`, только чтение.** 1420 строк анализа на 277 треков, `data` — 163,1 МБ. Из них `am-analyzer-12` — 10,3 МБ, остальные 152,8 МБ занимают версии 3–11. Файл базы весит 165 МБ. Подробности и польза — в Опт2.

### О4. `AnalysisService.get` при каждом вызове создаёт новый объект анализа

- **Место:** `apps/server/src/analysis.ts:252–255`: `return vocalActivity ? {...a, vocalActivity} : a`.
- **Что не так.** Кэш `bodies` в `packages/core/src/plan/fullmix.ts:114` и `vocalKeys` в `automix.ts:40` построены на `WeakMap` с ключом-объектом. Для треков с вокальной картой ключ каждый раз новый, поэтому кэш никогда не попадает. `bodyDensity` при каждом вызове заново копирует и сортирует кривую плотности, около 4000 точек. За одно планирование таких вызовов десятки, из `planIntroDrop`, `leadRiskSeconds`, `entrySkipCost` и других.
- **Польза.** Небольшая, доли миллисекунды на вызов.
- **Как исправить.** Кэшировать обогащённый объект в `memo` по паре `(hash, vocalActivity)`.
- **Риск.** Низкий.

### О5. Комментарий в `planBeatmatch` расходится с кодом

- **Место:** `packages/core/src/plan/planner.ts:1218–1228`.
- **Что не так.** Комментарий говорит: «every 4th downbeat … is a possible exit». Код же берёт все сильные доли второй половины A. Кандидатов выхода вчетверо больше, чем следует из комментария, а значит больше времени в цикле `bars × exits × entries`. Это одна из причин p95 ≈ 100 мс (Опт3).
- **Как исправить.** Комментарий надо поправить. Код менять только вместе с проверкой планов: прореживание кандидатов изменит выбор.

### О6. Перемотка во время перехода обрезает хвост эха без затухания

- **Место:** `packages/core/src/engine/mixer.ts:627–628`: `echo.reset()` и `voiceEcho.reset()` в `seek`.
- **Что не так.** Сама дека уходит за 6 мс, а 250 мс достаются другой деке. Звучащий хвост эха обнуляется в одном сэмпле, что может дать щелчок. В `abortTransition` (`mixer.ts:1212`) для голосового эха уже есть `fadeOut(0.15 с)`.
- **Доказательство.** Только чтение кода, щелчок не замерен.
- **Риск.** Низкий.
- **Цена.** Две строки: `fadeOut` вместо `reset`.

### О7. P10 молча пропускает финалистов с вокальной маской

- **Место:** `packages/core/src/engine/render-check.ts:45`: `if (… plan.vocalA || plan.vocalB …) return null`.
- **Что не так.** Полный микс включается, когда неизвестен хотя бы один голос. Если карта есть у одного трека, базовый план может нести `vocalA` или `vocalB`, и тогда рендер не делается вовсе. При этом `debug.renderCheck` не объясняет, что финалист не проверен, а только выставляет `metrics: null`.
- **Как исправить.** Передавать в рендер PCM голоса, он уже есть в `StemService`. Либо явно писать причину пропуска, чтобы в журнале было видно, что пара не проверена.

### О8. Скрытый дефект в повторе запроса чанков

- **Место:** `apps/web/src/audio/controller.ts:410` и `415`: `return this.fetchChunks(slot, run, attempt + 1)` без аргумента `part`.
- **Что не так.** Сейчас ветка недостижима для голоса: ошибки голоса обрабатываются раньше, в строке 400. Но если эту обработку однажды сдвинуть, повтор запроса голосового чанка запишет его в поток оригинала.
- **Цена.** Добавить `part` в два вызова.

### О9. `tools/stemless-ab.ts` привязан к `am-analyzer-12`

- **Место:** `tools/stemless-ab.ts:27`: `.all('am-analyzer-12')`.
- **Что не так.** P9 (локальная тональность, `an.local`) появляется только в `am-analyzer-13`, и на v12 `localClashFraction` всегда возвращает 0. Инструмент, которым проверяли полный микс, не может проверить P9. Отчёт о внедрении это и признаёт: «работа P9 на настоящих анализах версии 13 … не проверена». Дополнительно: все 70 треков с готовым v12 в `data-dev` — YouTube или Яндекс без локального файла.
- **Как исправить.** Брать `ANALYZER_VERSION` с откатом на предыдущую версию.

### О10. Одновременные `planChecked` для одной пары не объединяются

- **Место:** `apps/server/src/automix.ts:98–122`.
- **Что не так.** Подготовка пары и обновление после анализа могут прийти почти одновременно. Тогда планирование финалистов и рендер выполняются дважды.
- **Как исправить.** Хранить один выполняющийся Promise на ключ пары (`Map` с удалением в `finally`), как в `SharedPreparation`.
- **Риск.** Низкий.

## 2. Оптимизация

Порядок — по пользе.

### Опт1. iPhone: полный образ базы пишется в OPFS примерно раз в 5 с, пока играет музыка

- **Место:**
  - `apps/web/src/audio/controller.ts:1682`: `scheduleSave(true)` раз в 5 с во время игры;
  - `controller.ts:1753–1763`: `PUT /api/queue` со всей очередью и позицией;
  - `apps/server/src/routes/playback.ts:301–305`: `kvSet`;
  - `apps/mobile/src/worker/shims/sqlite.ts:115–136`: `changed()` → через 1,5 с `raw.export()` и `writeFile` всего образа во временный файл, затем `rename`;
  - `apps/mobile/src/worker/opfs-fs.ts:443–447`: `truncate`, полная запись, `flush`.
- **Что не так.** Любая запись, даже одной позиции, выгружает и пишет всю базу. Кроме того, `export()` в sql.js освобождает все подготовленные запросы: `generation++` в `sqlite.ts:129`, и после каждого сохранения все `StatementSync` компилируются заново.
- **Доказательство.** Код выше и замер `sqljs-export.cjs` на копии базы `data-dev` в памяти:
  - образ 164,8 МБ выгружается за 16 мс на ПК; после удаления старых анализов он весит 10,3 МБ;
  - запись идёт каждые ~5 с, это ≈ 2 МБ/с, или ≈ 7 ГБ флеш-записи в час даже на «чистой» базе в 10 МБ;
  - с анализами двух версий объём удваивается;
  - на каждую запись приходится временная копия образа в памяти worker.

  Время записи в OPFS на iPhone не замерялось.
- **Как исправить:**
  - (а) позицию и индекс воспроизведения хранить отдельно от sql.js: маленький файл в OPFS или `localStorage` страницы;
  - (б) в `sqlite.ts` откладывать сохранение до 30 с, пока приложение на переднем плане; при уходе в фон оставить немедленный `flushAll`, он уже есть в `worker/main.ts:46`;
  - (в) Опт2.
- **Польза.** Меньше расход батареи и износ флеш-памяти, нет периодических пиков памяти и CPU в фоне. Для фонового AutoMix это заметно.
- **Риск.** Низкий для (а) и (б): при аварийном завершении можно потерять до 30 с истории.
- **Цена.** (а) около 30 строк, (б) около 5 строк.

### Опт2. Удалять анализы старых версий

- **Место:** `apps/server/src/analysis.ts`.
- **Предложение.** Когда трек получил анализ текущей версии, удалять его строки старше предыдущей версии. Хранить текущую и одну предыдущую: инструменты сравнения пользуются предыдущей. После массовой очистки нужен `VACUUM`.
- **Доказательство.** О3: 152,8 из 163,1 МБ — версии 3–11.
- **Польза.** `data-dev`: −150 МБ диска. iPhone: образ sql.js не растёт после каждого обновления анализатора. Сейчас каждый переход на новую версию добавляет ещё по 10–40 МБ на 300 треков, и всё это пишется по Опт1.
- **Риск.** Инструменты повтора оценок (`rating-report.ts`, старые отчёты) могут хотеть историческую версию анализа. Для них старые строки лучше один раз выгрузить в `reports/`.
- **Цена.** Около 10 строк и тест.

### Опт3. `powerLevel` и `curveMean`: кэш линейной мощности

- **Место:**
  - `packages/core/src/plan/planner.ts:724–730`: `Math.pow(10, curve[i]/10)` в цикле;
  - `planner.ts:71–77`: `curveMean`;
  - `packages/core/src/plan/fullmix.ts:24–36` и `174–178`: то же самое.
- **Доказательство, профиль CPU.** `powerLevel` занимает 47,0 % времени планирования (`prof1`, 450 планов) и 60,9 % (`prof2`, планирование финалистов). Время одного плана, `bench.ts`, 150 пар:

  | Режим | Медиана | p95 | Максимум |
  |---|---:|---:|---:|
  | Без стемов | 8,5 мс | 107 мс | 182 мс |
  | Финалисты | 6,9 мс | 98 мс | 166 мс |
  | Со стемами | 9,4 мс | 62 мс | 224 мс |

- **Предложение.** Для каждой кривой (`rmsDb`, `lowDb`, `midDb`, `highDb`) один раз построить `Float64Array` с `10 ** (x/10)` и хранить в `WeakMap` с ключом-массивом кривой. Массивы кривых между запросами одни и те же, даже когда О4 создаёт новый объект анализа. Цикл суммирования остаётся тем же и идёт в том же порядке, поэтому результат побитово тот же, и планы не меняются: это проверяется через `stems.changed = 0`. Префиксные суммы дали бы O(1), но меняют округление, поэтому их стоит делать только отдельным шагом с проверкой.
- **Польза.** Ожидается в 1,6–2 раза меньше время планирования и рендер-проверки. Это важно для iPhone, где сервер работает в том же процессе. Ожидание основано на доле в профиле, после правки не замерялось.
- **Риск.** Очень низкий.
- **Цена.** Около 20 строк.

### Опт4. Лимитер: не считать true-peak, когда сигнал заведомо ниже порога

- **Место:** `packages/core/src/dsp/limiter.ts:123–150`: 24 отвода × 3 ветви × 2 канала = 144 умножения-сложения и 8 вызовов `crest` на каждый сэмпл, всегда.
- **Доказательство.** В профиле рендер-проверки (`prof3`) `processBlock` занимает 17,0 %, больше WSOLA (2,6 %) и кроссовера (7,0 %). Лимитер работает на каждом сэмпле и в живом AudioWorklet.
- **Предложение.** Вести максимум `|x|` по истории из 24 отсчётов. Если `max|x| · ‖h‖₁ · TRUE_PEAK_MARGIN < threshold`, то никакая интерполированная точка не превысит порог, и `req = 1` точно. Здесь `‖h‖₁` — сумма модулей ядра, она считается один раз. Свёртку тогда можно пропустить. Одна тонкость: `prevCL` и `prevCR` нужны следующему сэмплу, поэтому при выходе из пропуска надо досчитать ветвь 3/4 для предыдущей позиции из той же истории. Тогда выход совпадает побитово, это проверяется существующими golden-тестами лимитера.
- **Польза.** При громкости −16 LUFS большая часть сэмплов ниже порога, ожидается 2–3-кратная экономия CPU лимитера. Для iPhone в фоне это заметная доля всего движка.
- **Риск.** Низкий при побитовой проверке.
- **Цена.** Около 30 строк и тест.

### Опт5. Цена рендер-проверки и ленивые финалисты

- **Доказательство, `render-bench.ts`.** 22 рендера на ПК, 44,1 кГц: медиана 342 мс, максимум 699 мс на одного финалиста. Финалистов 2–5, то есть 0,7–3,5 с CPU на пару в основном потоке сервера. `stepAsync` уступает очередь, но это всё равно работа в event loop Fastify. На iPhone, по оценке, в 3–5 раз дольше; на устройстве не замерено.
- **Предложение:**
  - (а) финалистов со сдвигом баса на долю (P6) рендерить, только если у базового плана `lowHoleSeconds > 0` или `flams > 0`: сейчас рендерятся все пять;
  - (б) Опт3 и Опт4 сами снижают цену рендера;
  - (в) огибающую `env` для поиска двойных ударов (`render-check.ts:80–85`) считать скользящей суммой и только на участке перехода: сейчас она считается по всему рендеру, по 661 сэмплу на каждую миллисекунду.
- **Польза.** Обычно 2–3 рендера вместо 5.
- **Риск.** Низкий: базовый план проверяется всегда.
- **Цена.** Около 15 строк.

### Опт6. `arrivalFit` пересчитывает одни и те же уровни для каждого кандидата

В последнем сеансе (`v11-dj-8`, 22.10, 19:33–19:56) 7 из 12 сведений по битам длились 4 такта, 6,3–9,9 с. Разбор `debug` показал две причины:
- в 4 случаях (№271, 296, 300, 304) их выбрала альтернатива `short-phrase` в `chooseMusicalPlan`;
- в 5 случаях (№280, 293, 295, 299, 303) 4 такта обошли 8 по счёту на 0,05–0,23, через `lenPref` и `preferredBars`.

### П1. Длина сведения в секундах, а не в тактах

**Польза: высокая. Цена: низкая. Риск: средний.**

- **Место:** `packages/core/src/plan/planner.ts:1269–1270` (`preferredBars`, `lenPref`), `planner.ts:1201` (`barOptions`), `planner.ts:316–319` (`short-phrase`).
- **Сейчас.** Предпочтение 4, 8 или 16 тактов не зависит от темпа: 4 такта на 150 BPM длятся 6,4 с, а на 90 BPM — 10,7 с.
- **Алгоритм:**
  1. Целевая длина `D* = 12 с` для `normal` и `16 с` для `smooth`; `tight` остаётся без изменений.
  2. `lenPref = 1 − clamp(|log2(D/D*)| / 2)`.
  3. Мягкий нижний предел: при `D < 10 с` штраф `−0,15·(10 − D)/10`, как уже сделано в `fullMixCost` (`fullmix.ts:215`). Не действует для Next, режима «Короткие» и лимита `maxBlendSeconds`.
  4. Альтернатива `short-phrase`: вместо жёстких `[4]` такта брать наименьшее число тактов, дающее не меньше 10 с. Если такого нет, оставлять базовый план: защита слов B делается более ранним уходом голоса A при прежней длине.
- **Проверка.** `ab-planner.ts` на всей медиатеке: доля сведений короче 10 с, `lostB` и `voiceOverlap` должны не вырасти. Прослушать №271, 280, 295, 300.
- **Риск.** Длиннее общий участок — больше времени двум грувам, но при сведении по битам они стыкованы. Слова B защищает `first-words`, его гарантии проверяются тестами.

### П2. Конфликт тональностей: не укорачивать, а разводить середину по очереди

**Польза: высокая. Цена: низкая.**

- **Место:** `packages/core/src/plan/planner.ts:1245` (`if (keyClash && bars > 8) continue`), `planner.ts:1267–1269` (`dense = … || keyClash` → 4 такта), `planner.ts:1378–1381` (`midDuck`).
- **Сейчас.** Конфликт тональностей (часто ненадёжный на рэпе с 808) сокращает сведение до 4 тактов. Так получились 6–8-секундные переходы №271, 295, 300.
- **Алгоритм «гармонической очереди»:**
  1. При `keyClash` длина выбирается по П1.
  2. Середина и верх никогда не звучат вместе в полную силу. Середина B стоит на 0,18, пока середина A не опустится ниже 0,35. Затем середина A уходит до 0,2 за одну долю, а середина B открывается за следующую долю. Бас меняется на сильной доле, как сейчас.
  3. Приёмка: `tonalClashSeconds` (`fullmix.ts:101`) ≤ 1 с при известных локальных ключах (v13). Если ключи неизвестны, используется только глобальный ключ с `confidence ≥ 0.4`.
- **Проверка.** Рендер 10 пар с конфликтом: длина ≥ 10 с, провал ≤ 2 LU. Прослушать №295 и 300.
- **Риск.** Гармонический конфликт в общей полосе 180–2500 Гц на стыке долей. Смягчается шириной перекрытия в одну долю.

### П3. Динамическое приглушение середины B по огибающей A (сайдчейн «одна ведущая партия») — для полного микса и iPhone

**Польза: высокая. Цена: средняя.**

- **Место:** движок `packages/core/src/engine/mixer.ts` (`renderDeck`), `dsp/crossover.ts`; план — новое поле `TransitionPlan.duckB`.
- **Идея.** Без стемов ведущий голос A почти всегда сидит в средней полосе. Пусть середина B в перекрытии автоматически уступает A, когда A там плотная, и заполняет паузы A: дыхание и концы фраз. Это то, что радиоведущие делают с подкладкой, но по полосе.
- **Алгоритм в реальном времени, без выделения памяти:**
  1. В `renderDeck` для деки A после изолятора снять огибающую средней полосы: RMS 10 мс, атака 5 мс, спад 250 мс.
  2. Для деки B коэффициент середины `gm_B ← gm_B · max(floor, 1 − depth · clamp((envA_dB − ref_dB + 12) / 12))`, где `ref_dB` — уровень средней полосы A в теле трека (из анализа), `depth` до 0,6 (около −8 дБ), `floor = 0,35`.
  3. Включается только при неизвестном голосе A или B, только до `swapAt` и только при `gain_A·mid_A ≥ 0,5`.

  Для этого коэффициенты полос B должны считаться посэмплово: сейчас они интерполируются линейно на блок (`crossover.ts:75–88`). Деке B нужна вторая сумма по средней полосе — около 2 умножений на сэмпл.
- **Проверка.** `leadRiskSeconds` по рендеру, то есть по реальному выходу, а не по кривым. Пары без стемов из оценённых «голоса наложились»: №231, 242, 243.
- **Риск.** «Качание» подкладки B. Ограничивается спадом 250 мс и потолком −8 дБ. Под голосом A приглушается и инструмент B — по замыслу это и нужно.

### П4. Вход B «подъёмом» через фильтр высоких частот (аналог Rise из Spotify)

**Польза: средняя. Цена: низкая.**

- **Место:** `packages/core/src/plan/planner.ts:1367–1381` (полосы сведения по битам), полоса `filter` у деки B.
- **Сейчас.** B входит тонкой за счёт трёхполосных коэффициентов (`low 0`, `mid 0.4–0.7`, `high 0.25`). Это ступень на 180 Гц. Полоса `filter` (`dsp/sweep.ts`: `+1` — ФВЧ до 6 кГц, плавный TPT-фильтр без резонанса) у B не используется, только у A при `washout`.
- **Алгоритм.**
  1. При сведении по битам ≥ 8 тактов у B полоса `filter` идёт от `+0,55` (срез около 460 Гц) к `0` за последние 2 такта до `swapAt`, кривая `smoothstep`.
  2. Полоса `low` у B прежняя: обмен баса на сильной доле.
  3. `holdLoudness` не трогает `filter`. `fullMixCost.deckPower` уже учитывает его (`fullmix.ts:48`).
- **Польза.** Слышимое «нарастание» нового трека вместо резкого включения полос. Срез непрерывный, поэтому бочка B не появляется ступенькой, а ощущение «включили B» уходит. Это частая причина «резко».
- **Риск.** Фильтр на голосе B до смены основы окрашивает первые слова B, если B поёт рано. Отключать при `vocalB`, открытом до `swapAt`, и при неизвестном голосе B с плотным вступлением.
- **Цена.** Около 10 строк в планировщике.

### П5. Моно-низ на общем участке

**Польза: средняя. Цена: низкая.**

- **Место:** `packages/core/src/dsp/crossover.ts`, `StereoIsolator.processBlock`.
- **Идея.** Во время перекрытия низкая полоса каждой деки (< 180 Гц, уже выделена изолятором) сводится в моно: `low_L = low_R = (low_L + low_R)/2`. Две басовые линии и две бочки в стерео дают фазовые провалы и «кашу». В моно они складываются предсказуемо, и обмен баса звучит чище. Это стандарт мастеринга клубной музыки.
- **Алгоритм.** Флаг `monoLow`, плавно 0 → 1 за 0,3 с в начале перехода и 1 → 0 за 0,3 с после конца. Изолятор уже считает `low` отдельно для L и R, нужно одно смешивание на сэмпл.
- **Проверка.** Число `flams` и `lowHoleSeconds` в P10 до и после. Стерео-корреляция НЧ в рендере.
- **Риск.** Треки с широким стерео-басом (редко) немного сузятся только на время перехода.

### П6. Хвост реверберации без ритма для резкого конца A

**Польза: средняя. Цена: средняя.**

- **Место:** новая полоса `reverb` у деки A; `dsp/reverb.ts` (сейчас только общая маленькая комната, гребни 30–45 мс).
- **Чем отличается от отвергнутого.** Эхо всего микса отвергнуто, потому что повторяет ритм A поверх чужого. Реверберация не повторяет удары, она размазывает гармонию. И12 предлагала реверберацию только на голосе; здесь она для полного микса без стемов.
- **Алгоритм.**
  1. Условие: у A жёсткий финал (`naturalFade.length = 0`, уровень последних 1,5 с ≥ тело − 6 дБ), а у B до прихода основы есть дыра. Дыра — это `fullMixCost.unsupported > 0` или провал в P10 > 3 LU.
  2. Посыл в реверберацию открывается на последней доле A.
  3. Реверберация: FDN из 4–8 линий, RT60 2,5 с, ФВЧ 300 Гц (бочка и бас не размазываются), ФНЧ 6 кГц.
  4. Посыл только из A после фейдера (A уже стихает), хвост ниже −40 дБ до прихода основы B.
- **Проверка.** P10 `dipLU` на парах с `unsupported > 0`. Прослушать №256 и 259 («жёсткий стоп A»).
- **Риск.** «Эффект поверх» не всем нравится. Включать только там, где иначе была бы дыра.

### П7. Проверка сильной доли по малому барабану (правило, без нейросети)

**Польза: средняя. Цена: низкая.**

- **Место:** `packages/core/src/plan/planner.ts:518–522` (`gridTrust`), `barPattern` (`planner.ts:1153`) — акценты `kick` и `snare` уже есть в анализе.
- **Идея.** В 4/4 поп, рэп и рок малый барабан бьёт на 2 и 4 (позиции 1 и 3, считая с нуля). Если по всей песне `barPattern` даёт максимум малого на позициях 0 и 2, а бочка не повторяет этот рисунок, найденная сильная доля сдвинута на долю. Это типичная ошибка трекеров, о ней пишет и руководство Mixxx.
- **Алгоритм.**
  1. `s = snare[1] + snare[3] − snare[0] − snare[2]` по всей песне.
  2. Если `s < −0,3·mean(snare)` и `sd(snare) ≥ 0,3·mean`, понизить доверие к сильной доле: `downbeatConfidence·0,5` в `gridTrust`.
  3. Сведение тогда не выбирает выходы по фразам и использует ≤ 8 тактов.
  4. Половинный трэп (малый на третьей доле, позиция 2) правило не трогает: условие требует обеих позиций, 0 и 2.
- **Проверка.** Оценённые «сбился ритм» (№393, 396, 438, 443): сколько из них правило пометило бы. Ложные срабатывания — на хорошо оценённых.
- **Риск.** Жанры без бэкбита (хаус, драм-н-бейс) с их паттернами `snare` правило не тронет при малом `sd`.

### П8. Рендер-проверка: при равенстве выбирать более длинный вариант

**Польза: средняя. Цена: низкая.**

- **Место:** `packages/core/src/engine/render-check.ts:104–109`, `packages/core/src/plan/planner.ts:233–240` (финалисты).
- **Сейчас.** Финалист «вдвое короче» есть, «вдвое длиннее» нет. Замена плана разрешена только при провале базового.
- **Алгоритм.**
  1. Если базовое сведение по битам меньше 16 тактов и `D < 12 с`, добавить финалиста `fixed: {exit: aExit − bars·barA, entry: bEntry, bars: 2·bars}`, если он допустим: в пределах A, `maxBlendSeconds` и `regionA`.
  2. Он побеждает, если стоимость рендера не хуже базовой больше чем на 0,1, а `fullMixCost` — больше чем на 0,1.
  3. Предварительное условие — исправления О1 и О2.
- **Проверка.** Средняя длина, `dipLU` и `lostB` до и после на 300 парах.
- **Риск.** Длиннее — дольше пропуск финала A, но на соседней фразе.
