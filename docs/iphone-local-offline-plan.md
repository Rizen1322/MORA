# iPhone: локальный AutoMix и офлайн без арендованного сервера

Дата: 20 октября 2026. Это архитектурный план, реализация iOS в рамках текущей задачи не выполнялась.

Дополнение от21 октября: исследован реальный iPhone-форк Riff/Muriel, ветка `muriel`, commit `9dcaec6ac3a437ab34785f853d0e3e45aa1437de`. Он выполняет поиск/resolution на устройстве через Capacitor/native HTTP и JS extractor без Node subprocess. Следовательно, существующий UI можно сохранить в гибридной оболочке. Для нашего фонового AutoMix всё равно нужен независимый native audio host: сам Muriel отключает Web Audio DSP ради фонового воспроизведения. Подробная новая схема поиска, волны и загрузок — `iphone-muriel-source-architecture.md`.

## Вывод

Свой облачный вычислительный сервер не обязателен. Плеер, планировщик, анализ треков и подготовка переходов могут работать на iPhone. Сеть нужна для получения музыки/каталога/авторизации, если выбран удалённый источник. Загруженная доступная офлайн-музыка и собственные файлы должны играть в авиарежиме. Сборка и распространение iOS имеют отдельные требования Apple; это не аренда вычислительного сервера.

Простое размещение нынешнего сайта в WKWebView не переносит Node/Fastify/SQLite/Python/FFmpeg backend на телефон и не решает надёжное фоновое аудио. Для этого проекта рекомендован нативный audio host на Swift/C++ с SwiftUI или гибридным UI, где музыка и жизненный цикл принадлежат нативной части.

## Как разложить текущие компоненты

| Сейчас на ПК | На iPhone |
|---|---|
| AudioWorklet/mixer/WSOLA/DSP | AVAudioEngine + собственный real-time-safe AudioUnit/C++ DSP, предварительно проверенный одинаковыми golden vectors |
| FFmpeg decode / PCM HTTP chunks | AVAudioFile/AVAudioConverter для поддерживаемых форматов; ограниченные native ring buffers без HTTP между своими компонентами |
| TypeScript planner | Порт чистых функций в Swift/C++ или измеренный отдельный JS runtime; результат — те же JSON timeline/automation contracts |
| MIR-анализ | Фоновая очередь на устройстве, Accelerate/vDSP; current/next важнее сканирования библиотеки |
| Python stem models | Проверенная конверсия подходящей модели в Core ML либо отдельная mobile-модель; Python-процесс на iPhone не предполагается |
| Fastify/providers | Swift network adapters, URLSession, Keychain; сетевые запросы вне audio callback |
| SQLite/cache | Локальная БД и файловое хранилище, атомарные manifest/download операции |

AVAudioUnitTimePitch подходит для прототипирования, но не гарантирует идентичность нынешнему shared-WSOLA и alignment stems. Сначала сравнить задержку, фазу и качество, затем выбирать реализацию. Планировщик и native DSP должны учитывать latency и реальную частоту устройства, а не предполагать всегда44.1kHz.

## Три уровня подготовки

1. **Всегда доступный:** воспроизведение локальных файлов, gain/EQ, safe limiter, beat/cut/crossfade по уже готовым данным. Нет stems — музыкально осмысленный fallback без ожидания сети.
2. **Обычный on-device:** после импорта/загрузки посчитать loudness/true peak/tempo/grid/структуру. Перед началом песни подготовить ограниченный резерв следующих треков и 1–2 перехода.
3. **Тяжёлый вокальный режим:** separation нужных участков вокруг предполагаемых exit/entry, а не всей библиотеки одновременно. Малый batch, ограничение RAM, тепловой контроль, отмена старых задач, работа при доступном ресурсе. Конверсия модели в Core ML и скорость на реальном минимальном iPhone требуют отдельного прототипа. Поддержка Neural Engine не означает, что любая текущая модель автоматически на нём работает.

Дополнительный режим: подготовить треки/stems на собственном ПК и передать пакет по локальной сети/Files/AirDrop. После передачи ПК не нужен для прослушивания. Это необязательное ускорение, не обязательный сервер.

## Фон и батарея

AVAudioSession category playback + UIBackgroundModes audio обеспечивают фоновое прослушивание при блокировке. Реализовать interruption/route change, MPRemoteCommandCenter/Now Playing и отключение наушников. Silent mode не должен внезапно останавливать музыкальное приложение.

BackgroundTasks не дают гарантии, что iOS запустит произвольный большой анализ точно перед переходом. Не строить архитектуру на «телефон всегда ночью всё досчитает». Background processing — возможность с expiration/cancel, playback — отдельная непрерывная задача. Новые APIs продолжения пользовательских работ использовать только после проверки версии iOS и правил их применения. Готовить следующий переход заранее; если подготовка не успела, текущий звук не блокировать.

На audio thread запрещены сеть, файловое I/O, ML inference, locks с неопределённым ожиданием и выделение больших буферов. Анализатор и GPU-анимации выключаются при скрытом UI; музыка продолжает играть. При thermal pressure/Low Power Mode уменьшать анализ/separation, а не ухудшать стабильность render callback. Сначала измерения на устройстве, потом обещания автономности.

## Офлайн как отдельный продуктовый режим

- В меню трека/плейлиста: «Скачать», прогресс, отмена, повтор, «Доступно офлайн». У плейлиста показывать частичную готовность, а не общий успех, если один файл не загружен.
- Состояния: queued/downloading/verifying/preparing/ready/failed. Ready только после полной загрузки, проверки контейнера/длительности и атомарного перемещения из .partial.
- Оригинальный файл, обложка, metadata и analysis — единый версионированный manifest. Stems опциональны и восстанавливаемы; отсутствие stems не делает скачанный трек недоступным.
- URLSession background downloads, resume по поддержке сервера; истёкшие ссылки обновляются через provider adapter. Не путать HTTP cache с гарантированной офлайн-копией.
- Параметры: Wi-Fi only, лимит объёма, свободное место, отключение подготовки на батарее. Current/next и явно скачанное закреплены; LRU удаляет только незакреплённый cache. Удаление offline download не должно удалять собственный оригинал из Files.
- Собственные файлы импортируются через document picker с корректной работой security-scoped resources либо копируются в sandbox. Явно отличать импорт-копию от ссылки на внешний файл.
- Без сети волна использует доступные скачанные рекомендации/локальный резерв. Новую серверную подборку Яндекса без сети получить нельзя; UI объясняет «Офлайн-подбор из скачанного». Не выдавать локальную подборку за свежую персонализацию Яндекса.
- Реакции/история синхронизируются через устойчивую очередь с idempotency/dedup, привязкой к аккаунту и реальными допустимыми provider events. Переключение аккаунта не отправляет старые действия новому пользователю.

Каталог провайдера, проигрывание и разрешение хранить/обрабатывать аудиофайл — разные возможности. Текущий неофициальный Yandex MP3 adapter на ПК не является гарантией стабильной или допустимой iOS-дистрибуции/офлайн-функции. Не извлекать и не расшифровывать кэши других приложений; для каждого источника проверять доступный API/SDK, условия и DRM. Надёжный первый офлайн-релиз можно сделать на собственных импортированных файлах. Для API/лицензий конкретного сервиса нужна отдельная проверка на момент реализации.

## Этапы и приёмка

1. Нативный playback двух локальных файлов, gapless/seek/limiter; звук при блокировке30+мин, смена наушников/звонок.
2. Порт planner/DSP с общими JSON fixtures, совпадение timeline и измеримых параметров, blind listening текущих сложных пар.
3. Импорт/офлайн downloads/manifest/cache, авиарежим и перезапуск, мало места, незавершённая загрузка.
4. Core ML separation прототип на минимальном устройстве: время подготовки30сек окна, peak RAM, energy/thermal, качество остаточного вокала. По результату включить нужный tier, не требовать full-stems любой ценой.
5. Provider integration, реакции/settings, пользовательская бета; юридические и App Review вопросы отдельно.
