# Apple AutoMix и собственный движок

Проверено 19 октября 2026 года. Источники ниже прочитаны как документация; Apple Music на этом компьютере не запускался. Здесь реализован собственный движок с похожими принципами.

## Что опубликовано Apple

Apple описывает AI-анализ аудиопризнаков, beat matching и time stretching для индивидуальных переходов между песнями. [Apple Newsroom, 10.06.2025](https://www.apple.com/newsroom/2025/06/apple-services-deliver-powerful-features-and-intelligent-updates-to-users-this-fall/).

Выбор перехода зависит от музыки: возможны удаление начальной/конечной тишины и простой кроссфейд. Последовательное прослушивание альбома и некоторые жанры обходятся без перехода. [Руководство iPhone](https://support.apple.com/guide/iphone/transition-songs-iphadf2fe1f4/ios), [руководство Mac](https://support.apple.com/en-lamr/guide/music/-muse5e9ec085/mac).

Apple указывает ограничения для несовместимых темпов/жанров, загруженных пользователем файлов и покупок iTunes. Функция рассчитана на контент подписки Apple Music. Обещание сложного beatmatch для любой пары не соответствует официальному описанию. [Apple Support](https://support.apple.com/en-us/105067).

## Что по открытым материалам установить нельзя

В найденных официальных материалах нет архитектуры/весов модели, обучающих данных, формулы оценки cue points, названия time stretcher, правил обработки баса или точной границы вычислений между сервером и устройством. Не подтверждено использование конкретного separator, распознавания припева, LLM, Neural Engine или Rubber Band. Патент сам по себе не доказывает использование алгоритма в продукте.

Правило «Apple всегда начинает следующий трек с припева на 20–30 секунде» документально не подтверждено. Вход внутри трека можно реализовать самостоятельно, оценивая структуру музыки без фиксированного смещения. [Обсуждение MusicKit](https://developer.apple.com/forums/thread/792669) содержит вопросы пользователей, а не спецификацию AutoMix или подтверждённый API.

## Реализация для своих файлов

Конвейер: `анализ → выбор пары cue → TransitionPlan → две деки AudioWorklet`.

1. **Гипотезы темпа.** Рассматриваем обычный, половинный и двойной темп. Это помогает паре 87/174 BPM, но не превращает произвольные 100/143 BPM в совместимую ритм-секцию.
2. **Музыкальный вход.** Ранжируем границы секций, фраз и сильные доли по энергии, изменениям спектральных полос и плотности середины. Допускаем вход с 20–30 секунды, когда он выигрывает у начала по оценке всей пары. Лимит пропуска по умолчанию 45 секунд; режим «Сохранять начало» запрещает пропуск слышимого начала. Секцию не называем припевом: семантического классификатора нет.
3. **Длительность под пару.** Короткие 1/2/4-тактовые переходы расширяют применимость, когда длинное 8/16-тактовое сведение не помещается или создаёт конфликт. Лимит наложения проверяется после расчёта фактического tempo glide.
4. **Согласованный темп.** При glide деки сохраняют отношение скоростей. Запас исходного аудио и момент смены баса считаются по интегралу карты темпа. Предел растяжения проверяется для обеих дек.
5. **Несовместимый ритм.** Короткий переход на музыкальной границе и ограниченный echo handoff позволяют сменить BPM без длительного наложения двух ритмов. Для слабого/живого ритма остаётся мягкий кроссфейд, для альбомов — gapless.
6. **Стерео и громкость.** Нормализация, полосовой handoff и lookahead limiter. Поиск совпадений WSOLA учитывает стереоканалы, чтобы противофазный материал не исчезал из оценки.
7. **Подготовка.** Ревизии очереди и настроек отсекают устаревшие HTTP-ответы. После обновления анализа cue и план пересчитываются. Тайминг определяет счётчик сэмплов; UI-таймеры не совмещают биты. Вытесненный PCM можно загрузить снова после перемотки.
8. **Промежуточный BPM.** Если полное изменение темпа не укладывается в лимит, обе деки могут сойтись в общем темпе, соблюдая предел каждой деки. B молчит во время начальной смены темпа A, затем сетки совмещаются; после наложения B восстанавливает собственный BPM. Это собственная стратегия, её использование Apple не подтверждено.
9. **Синкопы и смена темпа.** Прямая проверка onset-сетки восстанавливает устойчивый пульс, когда DP-трекер цепляется за синкопы. Дополнительно проверяются активные 12-секундные участки и окончание: изменение BPM внутри трека не объявляется постоянной сеткой только по большинству ударов.
10. **Ручной Next.** Первое нажатие рассчитывает короткое сведение с учётом текущего участка A. Повторное нажатие быстро завершает переключение. До смены cue B его PCM загружается отдельно, поэтому поздний HTTP-ответ и повторное нажатие не оставляют деку без аудио.

11. **Голос.** Если локально подготовлена партия Hybrid Demucs, план ведёт голоса отдельно от инструментала: одновременно звучит один голос, старый заканчивается не позже смены основы, по возможности в паузе, новый открывается в начале своей фразы. Последнее слово старого голоса может уйти в отдельное эхо только по вокалу, которое затихает ниже −40 дБ до нового голоса. Подробности: [dj-automix.md](dj-automix.md).

Обязательных моделей/GPU нет, внешние сервисы не получают локальные файлы. Без подготовленной партии плотность середины остаётся эвристикой конфликта инструментов, а не детектором голоса. С партией используется измеренная активность голоса Demucs (10 Гц); это не распознавание слов или смысла. Downbeat и фразы предполагают 4/4; нестабильный ритм требует осторожного наложения.

## Присланное описание Spotify/Apple: что применимо

В октябре 2026 года пользователь прислал текст-спецификацию «как устроены AutoMix и Spotify Mix». Источников в нём нет. Утверждения о внутреннем стеке (Echo Nest/LLark у Spotify, нейронная разметка Apple, отключение AutoMix для Hi-Res Lossless, TCN/HMM-трекеры) в официальных материалах не подтверждены и здесь не считаются фактами. Полезная часть — общие DSP/MIR-принципы. Ниже они сопоставлены с проектом.

| Принцип из текста | В проекте |
| --- | --- |
| Офлайн-анализ и лёгкий манифест для плеера | Да: фоновый анализ сервера, `TrackAnalysis` в SQLite, план считается до перехода |
| Сетка битов, сильные доли, локальная карта темпа | Да: глобальная сетка и измеренные локальные участки (`beatRegions`); 4/4 предполагается |
| Хрома и Камелот | Да: хрома-профиль, тональность, совместимость по Камелоту |
| При тональном конфликте — короче наложение или echo | Да: ограничение тактов и приглушение середины при `compatibility < 0.5` |
| Структура по новизне/самоподобию | Упрощённо: новизна по хрома/энергии, без полной SSM |
| Не накладывать два вокала (V(t) < 0,15 — лучшее окно) | Да, сильнее: при разделённых партиях голоса передаются по одному; выбор точек штрафует наложение, где пришлось бы заглушать слышимое пение |
| Tempo morphing, B выходит на родной темп к концу | Да для beatmatch glide; у tempo_bridge B возвращается за 2–6 с после наложения |
| Фазовый вокодер + WSOLA для транзиентов | Частично: WSOLA с защитой атак, без фазового вокодера |
| Equal-power кривые | Да |
| Bass swap фильтрами LR4 | Да: трёхполосный LR4-изолятор, смена баса на сильной доле |
| LUFS-нормализация и lookahead-лимитер −1 dBTP | Нормализация есть; лимитер ограничивает sample peak −1 dBFS, true-peak (передискретизация) не реализован |
| Smart Reorder (TSP по BPM/тональности) | Нет: порядок очереди задаёт пользователь, «Моя волна» использует рекомендатель |
| Ручной Next — мгновенный микро-фейд | Иначе: первое нажатие — короткое музыкальное сведение, повторное — быстрый переход (настраивается) |
| Seek в зону выхода без прогретого буфера — без AutoMix | Близко: при неготовом буфере план превращается в короткий кроссфейд; gapless остаётся gapless |

## MIR: независимые источники

Глобальный BPM не гарантирует правильную фазу и постоянный темп выбранного участка. Классический подход использует onset strength и согласованность последовательности ударов: [D. Ellis, 2007](https://www.ee.columbia.edu/~dpwe/pubs/Ellis07-beattrack.pdf). Для структуры существуют методы повторяемости и временной сегментации: [librosa recurrence matrix](https://librosa.org/doc-playground/latest/generated/librosa.segment.recurrence_matrix.html), [agglomerative segmentation](https://librosa.org/doc/0.10.2/generated/librosa.segment.agglomerative.html). Это MIR-источники, не описание технологии Apple. Наш быстрый анализ секций проще этих методов.

## Проверка

- Планировщик: близкий и half/double BPM, большой разрыв, структурный вход, сохранение начала, короткие файлы, лимиты stretch/наложения и запас исходников по tempo map.
- DSP: pitch на стерео/противофазном сигнале, echo tail, точный gap, pause/seek/skip и цепочка переходов.
- Контроллер: изменения очереди во время HTTP, применение настроек к готовой паре, повторная загрузка вытесненного PCM.
- Матрица синтетических музыкальных примеров: `npm run eval:transitions`. Это техническая проверка, не оценка музыкальности слушателями. Пики и LU сами по себе не определяют качество сведения.
- Файлы для прослушивания: `npm run demo:transitions`; точные планы лежат рядом с MP3.

Автоматические проверки не заменяют прослушивания разнообразной реальной библиотеки. В отчёте отдельно указываются численные проверки, проверки в браузере и проверка человеком на слух.
