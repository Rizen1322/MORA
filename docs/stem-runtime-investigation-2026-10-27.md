# Почему stemMixing=true, но вокальные маски отсутствуют

Исследование GPT-6 Astra low после отрицательной оценки bar-entry-v3. Рабочая БД читалась read-only, настройки, оценки и исходное аудио не изменялись. После проверки локальных ресурсов основной агент разрешил ограниченную изолированную сепарацию #204; её результаты ниже. Загрузок и изменений приложения нет.

## Установленная причина

Desktop намеренно отключает подготовку вокала. `apps/desktop/src/main.mjs:140` передаёт `STEMS_PYTHON: ''`, заменяя даже внешнее значение переменной. `apps/server/src/config.ts:68` превращает это в `stemsPython: null`, следующая строка задаёт `stemsModels: null`. Это явная политика, а не потерянный флаг.

`apps/desktop/scripts/build.mjs:53` удаляет старые build/tools и build/vocal перед упаковкой. В `apps/desktop/electron-builder.json` среди extraResources нет модели, Python и инструментов разделения. `apps/desktop/scripts/check-backend.mjs:40` специально проверяет `health.stems.available === false` и runtime=null. В установленном `C:/Users/aivaz/AppData/Local/Programs/MORA/resources` действительно нет vocal; в `C:/Users/aivaz/AppData/Local/MORA/desktop.json` stemsPython=null.

`stemMixing=true` разрешает использовать доступные голосовые данные, но не устанавливает и не запускает separator. В `apps/server/src/app.ts:95` значение даже восстанавливается в true при отсутствии Python: прежний общий флаг также отключал связанные приёмы. Текущая настройка в read-only БД — true. Само значение не подтверждает доступность вокала.

## Цепочка подготовки и исполнения

1. `/api/analysis/focus` передаёт текущий/следующий треки в `StemService.focus` (`apps/server/src/routes/playback.ts:111`).
2. `StemService.ensure` (`apps/server/src/stems.ts:257`) немедленно выходит без cfg.stemsPython; pump также защищён этим условием. При отсутствии готового кэша status возвращает unavailable (`:175`). Это не очередь, не таймаут и не сбой GPU.
3. Готовый кэш проверяется по metadata.json, размеру vocal PCM и активности (`stems.ts:124`). `app.ts:89` подключает `stems.activity` к `AnalysisService`, который добавляет её в анализ на чтении (`analysis.ts:311`). Старые готовые кэши можно читать и без Python.
4. Без activity обоих треков `packages/core/src/plan/vocals.ts:291` переходит в одностороннюю обработку; без данных обеих сторон маски не создаются. В engine маска управляет формулой `original + (voiceGain - 1) * separatedVocal` до общей WSOLA (`packages/core/src/engine/vocals.ts`). Одной настройки или полосового EQ для такой операции недостаточно.
5. В офлайн-рендере `packages/core/src/engine/arm.ts:84` нетихая маска без vocal PCM — ошибка, а не выдуманный stem. В рабочем playback отдельно запрашиваются `/vocals/pcm`, готовность проверяется перед применением масок.

Для #198, #204, #205 и #189 проверены записи из живой БД и локальные пути. Все семь уникальных треков — provider youtube; для каждого отсутствует каталог `cache/stems/<content_hash>/hdemucs-v1` и metadata.json, а сохранённый анализ am-analyzer-14 не содержит vocalActivity. Во всех четырёх записанных планах vocalA/vocalB отсутствуют. Поэтому masks=false соответствует реальному отсутствию подготовленных партий; положительный #189 тоже работает без них.

UI не обещает работающий separator: `apps/web/src/pages/Settings.tsx:224` показывает переключатель только при health.stems.available. Его скрытие в desktop согласуется с текущей политикой. Косметическая правка ради видимости активности не нужна.

Python запущен с `-B`; импорты torch и torchaudio прошли, pipeline существует. Архив по archiveSha256 не проверялся — проверены перечисленные распакованные файлы.

## Конкретный следующий шаг

Исправимого дефекта, который включил бы достоверные маски без изменения явной продуктовой политики, не обнаружено. Автоматически включать separator в установленном приложении нельзя считать обычным исправлением.

Для отдельного ограниченного исследования скачивание не требуется: проверенный `apps/desktop/vendor/vocal/python.exe`, существующий `tools/separate-vocals.py`, локальные исходники из remote/PCM-кэша и отдельный новый каталог результатов. В выполненной пробе `TORCH_HOME` указывает на абсолютный `apps/desktop/vendor/vocal/models`; дополнительно загрузчики и сетевые вызовы заблокированы. Выбраны CPU и shifts=1 явно.

Для возврата этой возможности в продукт потребуется отдельное решение об упаковке/опциональной установке runtime, хранении и очереди подготовки, а также проверка времени и памяти на целевом ПК. Текущие локальные размеры известны; короткая проба ниже не заменяет оценку целых треков и памяти. Код приложения не менялся; регрессионный тест на несуществующий исправленный дефект не добавлялся.

## Выполненная ограниченная проба #204

Все файлы находятся отдельно в `data-bench-results/stem-probe-204-2026-10-27`. Источники — существующие локальные WEBM двух треков. `source-provenance.json` записывает путь и content hash. Извлечены A [78,96] с и B [3,21] с, по 18 секунд, 44100 Hz stereo. Это покрывает записанное сведение с контекстом вокруг; separator использует окна 8 секунд и внутренний контекст 0,35 с. Результат может отличаться от разделения целого трека из-за нормализации/контекста.

`offline-probe.py` проверяет SHA модели и подменяет torchaudio download_asset разрешением только на этот локальный файл; torch.hub.download_url_to_file, urllib и socket connect запрещены. Каждый процесс ограничен таймером 180 секунд. Оба завершились: separator metadata.seconds A=2,42, B=2,36; полное время процессов с импортами около 4,9/4,7 секунды. Это измерения только двух 18-секундных фрагментов, не обещание скорости для полной медиатеки. Peak RAM не измерялась.

Созданы `A-voice.wav`, `A-accompaniment.wav`, `B-voice.wav`, `B-accompaniment.wav`. Все значения конечны; accompaniment вычислен как original−separatedVoice. Максимальная погрешность обратной суммы 5,96e−8 подтверждает числовую сборку, **не чистоту разделения и не отсутствие остаточного голоса**.

`render.ts` применил существующий applyVocalHandoff к замороженной геометрии записанного #204 с реальными activity/PCM. aExit и bEntry перенесены в локальные координаты отрывков; curves обрезаны теми же смещениями. Нет padding неизвестных участков значением «голоса нет», нет поиска новых cue. Длительность, swapAt, карты темпа и положения источников после обратного смещения проверены на неизменность. Рендеры имеют по 695810 кадров, переход начинается на 2-й секунде, pre/post=2 секунды:

- `original.wav`: исходная обработка полного микса на этих же отрывках, SHA `e6900552628132b79e433a4ed95e52cb85977d845ac233e153e96299794953de`.
- `separated-vocal.wav`: существующая передача раздельных голосов и её bleed-guard EQ, SHA `cbb4fd90595d7ec8b02bf86ec2af7ef6574aabf3f5936208d079c80c984008af`.

У обоих underruns=0, limiter reduction=0, значения конечны. Эти WAV не выдаются за побитовую копию старой страницы с другим sample rate и pre/post. Полный `report.json` содержит метрики, хеши партий и сведения о применённых масках.

Выявлено ограничение существующего вокального рецепта: cleanA=false, fadeA=0,45 с, выход A заканчивается на 5,821 с, голос B открывается с 6-й секунды. lostB=3,312 — внутренний взвешенный activity proxy, не точная длительность удалённых слов. Значит даже с настоящими stems рецепт может подавить существенное начало B и срезать A без найденной паузы. ASR/верифицированных границ слов нет; утечки separator на слух ещё не оценены. Проба демонстрирует работающий отдельный механизм, а не подтверждённо хороший переход. Следующий шаг — оценить эти аудио и отделённые партии; новые фазовые или фейдерные гипотезы не добавлялись.

Основной агент независимо сверил SHA-256 манифеста новой страницы `afe7c78ef7baaa95b9ce5ae74cbf0c60a785cb05acea371722da58d8e9bafc15`, четыре хеша WAV/планов и шесть хешей исходных отрывков, vocal PCM и metadata. Сравнением JSON подтверждены одинаковые aExit, bEntry, duration, swapAt, tempoA/tempoB, bDelay и gap. Проверены синтаксис JavaScript страницы, наличие текстового экспорта и automaticEnabled=false. Код приложения в этой итерации не изменён; широкий прогон тестов повторно не запускался.

Неизменяемая страница двух вариантов с абсолютными оценками и текстовой выгрузкой: `data-bench-results/review-real-stems-204-2026-10-27/index.html`. Манифест SHA-256 `afe7c78ef7baaa95b9ce5ae74cbf0c60a785cb05acea371722da58d8e9bafc15` содержит смещения/хеши исходных отрывков, vocal PCM и metadata, точный SHA модели и параметры запуска. Четыре хеша WAV/планов после записи проверены, JavaScript страницы синтаксически проверен; используется существующий absoluteExportBrowserScript с текстовым fallback. После подготовки страницы аудио и рецепты не менялись.
