## Задача и последний приоритет пользователя

Сначала прочитай корневой `prompt.txt`: там исходный запрос и первая работа Claude. Затем изучи текущий код и этот документ. Пользователь хочет AutoMix, воспринимаемый как работа диджея/Apple Music, с музыкальными входами внутри следующего трека, а не просто длинный кроссфейд. Разные BPM должны обрабатываться подходящей музыкальной стратегией, а не обязательным растяжением любой пары.

Последнее уточнение пользователя дословно:

> по сведениям по битам многие треки прям круто сводит, но бывает что прошлый трек там тип кто то еще поет но уже по биту он свел и играет некст трек но есть момент сведения и слышно вокал пред трека и прям бесит, обыграй как то это красиво

Значит, сохраняй удачное сведение инструментала, но музыкально заканчивай старый голос до вступления нового. Это главный следующий шаг. Не заменяй всё быстрым master fade и не обещай отсутствие артефактов разделения.

## Что уже реализовано

### Музыкальное планирование

- Beatmatch с half/double BPM, совместным tempo glide, обменом баса и восстановлением исходного темпа B.
- `tempo_bridge`: оба трека сходятся к допустимому промежуточному BPM. Лимиты stretch и потребление исходников считаются по интегралу карт темпа.
- Умный вход B по структуре/энергии/сильным долям, в том числе на 20–30-й секунде. Лимит пропуска по умолчанию 45 с, пользовательский 0–75 с; режим сохранения начала соблюдается. Это не семантическое распознавание припева.
- Новый `drop_mix`: при несовместимых BPM и наличии партий короткая инструментальная подводка B, смена баса/грува на выбранной сильной доле, короткий фильтрованный хвост A. Собственные темпы сохраняются; длительного несинхронного наложения двух полных ритмов нет.
- Локальные измеренные ритмические регионы `BeatRegion` на случай ненадёжного глобального BPM: `packages/core/src/mir/regions.ts`, интеграция в анализ/планировщик. Не экстраполируются через безударные разрывы/смену темпа. Глобальная устойчивая сетка остаётся предпочтительной. Размер/фразы пока предполагают 4/4.
- Первое нажатие Next запускает короткое музыкальное сведение из текущего места; повторное переключает быстро.

### Настоящие локальные вокальные партии

- `tools/separate-vocals.py`: официальный Torchaudio bundle `HDEMUCS_HIGH_MUSDB_PLUS`, 44.1 kHz stereo, сегменты 8 с с перекрытием 1 с, плавная сборка. Нейросеть работает локально на CUDA/CPU, модель скачивается один раз.
- На этой машине уже установлены Python 3.12, torch 2.7.1+cu118, torchaudio 2.7.1; NVIDIA RTX 3070 8 GB. Не устанавливай всё повторно без необходимости.
- `.env`: `STEMS_PYTHON=C:/Users/Rizen/AppData/Local/Programs/Python/Python312/python.exe`.
- `apps/server/src/stems.ts`: последовательная очередь, приоритет текущей/следующей песни, валидация кэша, прогресс/ошибки. Партия хранится как `vocals.s16` (stereo s16le, масштаб по пику в `metadata.storage.scale`, остаток квантования ≤ −98 дБFS RMS / ≤ −93.6 дБFS пик на всей медиатеке); API по-прежнему отдаёт f32le. Ресемплированных копий на диске нет: другие частоты считаются ffmpeg при чтении по диапазону, выровненному на период ресемплера, бит-в-бит как ресемплинг целого файла. Python пишет `vocals.f32`, сервер сразу сжимает её; `compactAll()` при старте сервера переводит старые f32 и удаляет `vocals.f32`/`vocals_<sr>.f32` только после проверки s16. Партии: `data-dev/cache/stems/<content_hash>/hdemucs-v1`; веса: `data-dev/cache/models`.
- Добавлен ограничитель размера генерируемого stem-кэша по `PCM_CACHE_MB`, pin используемых партий на 10 минут; удаление только внутри проверенного cache-root. Это отдельный бюджет от обычного PCM-кэша, а не общий суммарный лимит всего data-dir.
- Роуты `GET /api/tracks/:id/stems`, `GET /api/tracks/:id/vocals/pcm?sr&start&frames`; второй выдаёт stereo f32le. Соблюдаются ограничения источников.
- `TrackAnalysis.vocalActivity`: сглаженная измеренная активность выделенного вокала 10 Hz. Не транскрипция, не понимание текста/окончания фразы.
- План содержит `vocalA`/`vocalB`: отдельные карты амплитуды голоса. `packages/core/src/plan/vocals.ts` выбирает момент передачи. Настройка `stemMixing` включена по умолчанию.
- `packages/core/src/engine/vocals.ts`: перед одним общим стерео WSOLA применяется `original + (vocalGain - 1) * separatedVocal`. При gain=1 воспроизводится исходник; голос и инструментал не растягиваются независимыми движками.
- Engine, offline renderer, worklet и controller получили отдельную загрузку vocal PCM. Готовность партий обновляет планы через SSE, кэш плана учитывает наличие модели.

### Надёжность и интерфейс

- Исправлены гонки подготовки/очереди/analysis refresh, цепочка A→B→C, устаревшая позиция A при подготовке C, обработка ошибок входящей деки, ручной Next во время восстановления темпа.

## Статус после прохода 19.10.2026 (am-planner-13)

Шесть проблем из прошлой передачи исправлены и покрыты тестами. Подробности: `docs/dj-automix.md`, результаты: `docs/real-library-validation.md`.

1. Эхо со старым голосом: echo-send деки A закрыт, пока маска голоса не равна нулю для всех кадров, которые может перекрыть WSOLA (+45 мс). Акустический тест проверяет хвост.
2. Голос A заканчивается не позже swapAt: совместный выбор паузы A и начала фразы B, цена — заглушённое слышимое пение обоих (`debug.stems.lostA/lostB`). Если A пел до конца, его последнее слово уходит в вокальное эхо (lane `voiceEcho`, побочный канал WSOLA). Хвост рассчитан ниже −40 дБ к открытию голоса B.
3. Forced finish: голос A уходит за 0,2 с, вокальное эхо гаснет за 0,12 с.
4. Потеря PCM голоса A: вся дека A уходит к запланированному концу голоса (`retireOutgoingVoice`).
5. `fitPlan`: gapless (duration 0) не превращается в кроссфейд.
6. Тихий outro в tempo_bridge: `bridgeHole` в оценке моста. «Осень → В Лувре» −10,56 → −1,85 LU.

Дополнительно: цена `voiceClash` при выборе точек (слышимое пение одновременно у A и B); `StemService.prune` больше не удаляет партии треков из медиатеки (из-за этого пропали три готовые партии, их подготовили заново).

## Исследование и ограничения

Apple официально подтверждает AI-анализ, beat matching/time stretching, но не раскрывает точные модели/архитектуру/алгоритм cue и не подтверждает использование Demucs. Наше разделение — собственное техническое решение, не копия внутренних технологий Apple.

Наш локальный анализ ритма — собственная реализация; GPL MATLAB Tempogram Toolbox не включался. Нейросетевой вокал может оставлять bleed/артефакты; карты активности не понимают текст. GPU нужен для удобной скорости подготовки, не для исполнения готового перехода. При отсутствии готовых партий остаётся прежний безопасный DSP fallback.
