# Riff и MORA: сравнение исходников перед выпуском 0.3.6

Дата: 22 октября 2026. Это read-only аудит кода: Riff не запускался, зависимости не устанавливались, сервер и воспроизведение MORA не прерывались. Изменён только этот отчёт. Ponytail full: переносить конкретные полезные решения, сохраняя действующий движок и ограничения ресурсов.

**Главный вывод:** у Riff стоит перенять устойчивость поиска, подготовку по намерению пользователя и каталог без Яндекса. Он не содержит более совершенного DJ AutoMix. Его сетевой код также не объясняет автоматически, почему официальный YouTube работает у друга, а MORA нет. Новая реализация сетевого транспорта MORA 0.3.6 уже отличается от Riff в полезную сторону.

## Сеть: почему нельзя просто скопировать Riff

В Riff YTM ходит через Node `https.request`, downloader через Python/yt-dlp, audio CDN — через Chromium `<audio>` или hls.js. Следовательно, «страница YouTube открывается» не проверяет путь YTM metadata и extractor. В просмотренных сетевых участках Riff нет передачи `session.resolveProxy` загрузчику и нет Chromium `net.fetch` для YTM.

В текущей MORA 0.3.6 уже есть:

- Chromium transport для YTM в desktop utility process: [backend.ts](../apps/desktop/src/backend.ts).
- Разрешение системного прокси отдельно для YouTube и SoundCloud перед стартом backend: [main.mjs:99](../apps/desktop/src/main.mjs#L99), [public-network.mjs](../apps/desktop/src/public-network.mjs).
- Раздельные circuit breaker `search` / `next` с 15-секундным cooldown: ошибка радио не должна блокировать поиск на минуты. [ytmusic.ts:29](../apps/server/src/public/ytmusic.ts#L29). У Riff YTM search после трёх неудач останавливает основной путь на 5 минут, но продолжает fallback.
- Приоритеты current / next / search / background, ограничение числа процессов, timeouts и ограничение вывода: [ytdlp.ts:83](../apps/server/src/public/ytdlp.ts#L83).

Это соответствует назначению [Electron net](https://www.electronjs.org/docs/latest/api/net): Chromium network stack доступен в main/utility, поддерживает системные proxy/PAC. Сам по себе он не копирует профиль, расширения и маршрутизацию стороннего браузера. Браузерный VPN/DPI extension и обязательная авторизация proxy остаются отдельными причинами расхождения. PAC, зависящий от CDN hostname, также требует отдельной проверки: один proxy, выбранный для YouTube, не обязательно является правильным для каждого CDN.

**Не переносить:** `--no-check-certificates` из Riff [server.js:1311](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/server.js#L1311) и `webSecurity: false` [main.js:220](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/main.js#L220). Это ослабление защиты, а не корректное исправление сети. MORA сохраняет CSP, изоляцию renderer и закрытый launch token: [main.mjs:26](../apps/desktop/src/main.mjs#L26), [app.ts:124](../apps/server/src/app.ts#L124).

## Очередь, прогрев и радио

**Где полезен Riff:**

- Дедупликация незавершённого поиска: второй одинаковый запрос подписывается на уже существующий Promise. [server.js:1479–1497](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/server.js#L1479-L1497). MORA кэширует готовые поиски LRU, но сам `PublicMusic.search` не объединяет одинаковые незавершённые запросы.
- Прогрев URL первого результата после поиска и hovered строки через 300 мс. [server.js:1513](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/server.js#L1513), [app.js:6164](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/app.js#L6164). Это именно resolve URL, а не загрузка всей композиции.
- Кандидаты рекомендаций не только из YouTube Mix: объединяются Deezer related artists и artist radio, совпадение из нескольких источников усиливает оценку. [server.js:681–801](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/server.js#L681-L801). Лайки получают больший вес, есть ограничение повторов исполнителя и повторно предложенных песен. Это полезный способ расширять кандидатов, **не ML-модель предпочтений и не доказанная рекомендация лучше нашей**.

**Где MORA уже лучше/не нужно дублировать:**

- `CatalogPlayer` готовит выбранный трек и два следующих; refill online-radio начинается, когда остаётся меньше 10 кандидатов. Удаление upcoming треков не отнимает ownership станции. [catalog-player.ts:29](../apps/web/src/lib/catalog-player.ts#L29), [catalog-player.ts:130](../apps/web/src/lib/catalog-player.ts#L130), [radio.ts:69](../apps/web/src/lib/radio.ts#L69). В Riff next-prefetch из timeupdate запускается после половины трека: [app.js:5388](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/app.js#L5388).
- Наш ранкер уже учитывает текущие лайки/дизлайки, 2-часовую давность проигрывания, разнообразие, энергию и BPM/Camelot **когда анализ известен**. [radio-taste.ts](../apps/web/src/lib/radio-taste.ts), [RadioTuning.tsx](../apps/web/src/components/RadioTuning.tsx). Обещать BPM-совместимость любого ещё не загруженного кандидата нельзя.
- SharedPreparation объединяет подготовку аудио, но отменяет общий worker только после ухода всех подписчиков. Это хорошая готовая база для поиска; не следует заменять её голым Promise без индивидуальной отмены. [shared-preparation.ts](../apps/server/src/public/shared-preparation.ts).
- Риск Riff: `normalizeArtistName` удаляет всё, кроме `\w`, пробелов и нескольких знаков; кириллические имена теряют значимую часть. [server.js:329](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/server.js#L329). Наш `normalizeMusic` использует Unicode letters/numbers. Не копировать этот normalizer для русской библиотеки.
- Нормализация версий Riff агрессивно убирает квадратные скобки и feat из названия. Такая дедупликация способна склеивать разные записи. Нужны сохранённые версии/длительности и confidence, а не просто одна строка.

## Кэш, офлайн и нагрузка

У Riff удачная простая схема для обычного плеера: CDN-поток начинается раньше фонового сохранения. Но через 10 секунд он отдельно запускает yt-dlp для сохранения Opus 128K: возможны повторное получение данных и лишняя обработка. Его `pruneDiskCache` удаляет старые `.temp.` и совсем маленькие файлы; **в этой функции нет бюджета для готового cache audio**. [server.js:187–213](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/server.js#L187-L213), [1224–1288](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/server.js#L1224-L1288). Это не образец для решения прежнего заполнения диска C.

В MORA уже есть LRU audio cache, отдельный pinned offline status, сериализация eviction, защита текущих файлов; clear cache не удаляет скачанное. Стандартный audio cache — 512 MiB; PCM и stems имеют **свои** бюджеты, поэтому число в одной настройке не равно суммарному занятию диска. [downloads.ts:71](../apps/server/src/public/downloads.ts#L71), [downloads.ts:199](../apps/server/src/public/downloads.ts#L199), [downloads.ts:233](../apps/server/src/public/downloads.ts#L233), [config.ts:56](../apps/server/src/config.ts#L56), [pcmCache.ts:261](../apps/server/src/pcmCache.ts#L261). Здесь не нужны два конкурирующих cache manager.

Важная цена нашего DSP: float32 stereo PCM при 48 kHz — около **23,0 MB/мин** (48 000 × 2 × 4 × 60). Это производные данные, а не ещё один скачанный mp3. Для iOS нужно отдельное решение о временных PCM-окнах и бюджетах, а не просто уменьшенный CSS. Riff, проигрывающий compressed media через `<audio>`, не оплачивает тот же объём анализа/двухдекового PCM.

У Riff есть пользовательский экспорт аудио с metadata/embedded cover и форматами, но экспорт lossy-source в FLAC не восстанавливает потерянные данные. [server.js:2436–2448](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/server.js#L2436-L2448). MORA offline уже сохраняет исходную запись, а backup плейлистов экспортирует только метаданные: [backup.ts](../apps/server/src/routes/backup.ts). Экспорт размеченного аудиофайла — отдельная функция, не исправление качества исходного звука.

## Звук и DJ-переходы

Riff — полезный reference для набора настроек, но **не улучшенный DJ engine**:

- Crossfade привязан к `timeupdate` и последним X секундам; вызываются fadeOut / playNext / fadeIn. Нет обнаруженной beatgrid/phrase/vocal-aware двухдековой синхронизации. [app.js:5370–5385](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/app.js#L5370-L5385).
- Real-time pitch в `applySettings` вычисляет playbackRate как `speedPitch × 2^(pitch/12)` и выключает preservesPitch. Поэтому именно этот realtime путь меняет длительность при изменении pitch; описание README про полностью независимый pitch нельзя считать доказанным. [audio-engine.js:472–486](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/audio-engine.js#L472-L486).
- Есть 10-band EQ, reverb, echo, distortion, уровни, плавная установка некоторых параметров; limiter реализован DynamicsCompressor, а не обнаруженным polyphase true-peak DSP. [audio-engine.js:149–164](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/audio-engine.js#L149-L164), [196–246](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/audio-engine.js#L196-L246). Субъективное качество по одному графу не определяется.

MORA уже содержит анализ структуры/темпа/тональности, планирование вокальных окон, master-tempo, отдельные decks, переходный EQ и room effects, независимые transport speed/pitch в пределах настроек. [planner.ts](../packages/core/src/plan/planner.ts), [vocals.ts](../packages/core/src/plan/vocals.ts), [mixer.ts](../packages/core/src/engine/mixer.ts), [playback.ts](../packages/core/src/dsp/playback.ts). MasterTone вычисляет запас по реальной EQ curve; последний limiter использует lookahead и 4× оценку true peak. [tone.ts:75](../packages/core/src/dsp/tone.ts#L75), [limiter.ts:50](../packages/core/src/dsp/limiter.ts#L50). Это архитектурное преимущество для нашей задачи; идеально звучащие переходы всё равно требуют калибровки и прослушивания.

В 0.3.6 параллельно меняются early handoff gain/EQ, pre-fader echo и границы вокального filter window. Их корректность оценивается отдельным AutoMix-аудитом; Riff не даёт соответствующих алгоритмов для переноса.

## UX / дизайн: что имеет смысл взять

- **Карточки артистов/альбомов без подключения Яндекса.** Riff строит artist page из Deezer metadata, Wikipedia biography и fallback YouTube search. [server.js:1870–1968](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/server.js#L1870-L1968). У MORA структурированный каталог artist/album в routes/catalog сейчас Яндекс-специфичный. Полезна сама связная навигация: исполнитель → записи → альбом → воспроизведение через наш resolver. Нельзя копировать Riff `isVerified = nb_fan > 30000`: число фанатов не означает подтверждение личности.
- **Цветовая система из обложки.** Riff генерирует surface/primary/secondary/tertiary роли; можно сравнить контраст и цельность нескольких ролей с текущими art-цветами MORA. [app.js:704–923](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/app.js#L704-L923). Не нужен перенос всего Material UI: сохранить нашу типографику, hierarchy и мобильные размеры.
- **Различимые compact/fullscreen/lyrics режимы**, поэтапная визуализация: полезны паттерны плотности, а не все настройки одновременно. Riff уменьшает FFT в скрытом окне и умеет suspend context после паузы. [audio-engine.js:554–585](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/audio-engine.js#L554-L585). В MORA уже есть hidden/offscreen ограничения, WebGL fallback в Canvas и desktop full-motion default; это не повод отключать экономию в скрытом окне.
- CSS editor, произвольные plugins, background video, distortion и большой audio editor не приоритетны перед стабильным воспроизведением/iOS. Они увеличивают поверхность поддержки и настройки, а не автоматически улучшают главную страницу.
- RTL lyrics как отдельный модуль — полезная небольшая идея для будущих арабских/иврит текстов: [lyrics-rtl.js](https://github.com/rootscripts/riff/blob/062c0f62539cda7ade077fd3e9b0eda0b1928925/lyrics-rtl.js). Перевод текстов и Discord пользователь исключил; не возвращать их в план из README.

## Крупные проекты, которые не надо незаметно добавлять к этому аудиту

1. **Прямой streaming в наш PCM decoder** из validated CDN URL с Range, обновлением истёкших URL, HLS, отменой и одним потоком записи в cache. Это может убрать ожидание некоторых контейнеров и повторный download, но не является переносом пары строк Riff. Нужны net/proxy parity, SSRF allowlist, backpressure, discontinuity/seek/reconnect tests и сохранение одного DSP engine. Отдельный второй `<audio>`-плеер обойдёт AutoMix и не решит задачу пользователя.
2. **Экспорт аудио с embedded cover/metadata, trimming и применением эффектов.** Офлайн и JSON-backup уже есть; нужен отдельный минимальный UX, атомарная запись, отмена и правдивое описание lossy→lossless. Перед iOS не приоритет.
3. **Нативная iOS source pipeline.** Riff — desktop Electron/Node/yt-dlp, не готовое iPhone-решение. В изученном snapshot нет подтверждения переносимой iOS реализации. Переносить можно bounded state machine, identity, ranking, offline manifest и DSP-идеи. Desktop executable/process/loopback assumptions нужно заменить и проверить на Mac/Xcode. Не вводить обязательный отдельный сервер ради повторения desktop subprocess.
