### 1. Перезапись running при совпадении реального содержимого

**Код:** [analysis.ts:182](../apps/server/src/analysis.ts#L182), строки 182–188; обработчик результата на строках 198–208. В релизной копии это 167–173 и 183–193.

Два разных внешних ID могут после скачивания дать одинаковый SHA-256. Пока хэши предварительные, оба задания разрешено запустить. После `resolveMediaPath()` каждый callback переносит запись в `running` под окончательный хэш через безусловный `set`. Второй затирает первый. Когда первый worker отправляет результат, поиск по `jobId` не находит его, `onMessage()` возвращается раньше `pw.busy = false`. Worker остаётся занят навсегда, хотя физически уже закончил. При двух workers теряется половина очереди; повторение сценария может остановить анализ полностью до перезапуска. Это потеря логического слота, а не доказанная утечка памяти worker.

**Подтверждение:** синтетические записи с разными исходными хэшами сведены к одному, оба callback разрешены, затем доставлены результаты обоих workers. В конце `running.size === 0`, но флаги workers равны `[true, false]`. Тест использует реальный `AnalysisService` и временную SQLite, подменяя только workers и получение файла.

**Минимальное исправление:** перед переносом на `fresh.content_hash` проверить уже выполняющийся/готовый анализ этого хэша. Не перезаписывать чужую запись; освободить лишний слот и присоединиться к существующему результату. Удаление записей должно проверять принадлежность конкретному `Running`, чтобы поздний callback не удалил чужое задание. Учитывать и уже поставленную очередь под новым хэшем.

**Что затронуть:** `AnalysisService.pump/onMessage`, тесты отмены/очереди и обновление хэша в `Library.resolveMediaPath/rebindContent`. API анализа и DSP менять не требуется.

**Критерий пользы:** одинаковый контент рассчитывается один раз, оба слота освобождаются, третье задание стартует. Содержимое анализа должно совпасть с результатом одиночного запуска; звук не меняется.

### 2. Точная длина PCM не доходит до проигрывателя

**Код:** [controller.ts:349](../apps/web/src/audio/controller.ts#L349), 454–480; [playback.ts:59](../apps/server/src/routes/playback.ts#L59); [mixer.ts:392](../packages/core/src/engine/mixer.ts#L392) и 1274. В релизном controller соответствующие строки — 333 и 438–464.

`loadSlot()` фиксирует `totalFrames` из `/prepare`, когда сервер ещё знает только длительность из метаданных. PCM API уже возвращает точные `X-Total-Frames` и `X-Complete`, однако `readChunks()` их не читает. Размер массивов и предел `ChunkStore` остаются прежними. Если длительность завышена, остаток заполняется нулями и плеер продолжает этот хвост. Если занижена, хвост исходного звука не попадает в store/запросы. Обновление DTO медиатеки само по себе размер уже загруженной деки не меняет.

**Подтверждение:** серверный ответ содержит 10 стереокадров и заголовки `X-Total-Frames: 10`, `X-Complete: 1`; при начальном `slot.totalFrames = 100` клиент создаёт 100 кадров, последние 90 — нули, и длину слота не исправляет. Обрезание при обратном соотношении следует из того же `expected` и предела store; этот обратный вариант отдельно не проигрывался через настоящий AudioWorklet.

**Минимальное исправление:** валидировать и принимать авторитетную длину завершённого PCM для оригинальной дорожки; передать уточнение в worklet отдельной командой с token текущей деки. Обновить длину слота и store без перезагрузки/сброса текущей позиции. Проверить заранее загруженный последний частичный chunk: после увеличения длины его может потребоваться запросить повторно. Не выводить EOF только из короткого ответа незавершённого декодера.

**Что затронуть:** controller, тип `EngineCommand`, обработчик worklet, длина original/vocal store в MixerCore, тесты controller и окончания дорожки. Формат f32 и DSP сохраняются.

**Критерий пользы:** тесты обоих направлений ошибки метаданных, включая пересечение границы chunk; последний настоящий сэмпл не теряется, добавленная тишина не проигрывается, событие `ended` приходит по реальному EOF. Проверить переход на следующую дорожку и seek около конца. Сравнение исходных PCM кадров — побайтное.

### 3. Отменённый PCM оставляет ненужную сетевую загрузку

**Код:** [provider.ts:211](../apps/server/src/public/provider.ts#L211), особенно 216 и 318–322; [pcmCache.ts:268](../apps/server/src/pcmCache.ts#L268); [ffmpeg.ts:62](../apps/server/src/ffmpeg.ts#L62); лимит очереди `apps/server/src/app.ts:69`, timeout загрузки `apps/server/src/public/ytdlp.ts:240`.

`playbackInput()` запускает `fetchAudio(src)` без `AbortSignal`. Общая подготовка корректно сохраняет загрузку, пока есть подписчик без отмены. Но при отмене декодирования `PcmCache` убивает ffmpeg, а его close лишь уничтожает читаемый поток. Этот путь не удаляет исходную подписку `fetchAudio`. Даже после того как поток больше никому не нужен, yt-dlp может продолжать качать файл до конца или таймаута 180 секунд. Быстрое переключение нескольких сетевых треков способно занять оба слота загрузчика устаревшими треками и задержать выбранный трек, расходуя сеть и диск.

**Подтверждение:** настоящий `PublicMusic.playbackInput` читает временный growing-файл от управляемой подмены загрузчика. После `input.destroy()` сигнал загрузки остаётся `aborted === false`; только `music.stop()` его отменяет. Настоящие сайты и реальные аудиофайлы не использовались. Величина экономии сети не измерена.

**Минимальное исправление:** дать записи PCM собственный AbortController и передать сигнал в `playbackInput`/`fetchAudio`; снять именно её подписку при отмене записи. Существующий `SharedPreparation` уже умеет сохранять загрузку для остальных читателей. Не вызывать безусловный abort общей transfer: офлайн-загрузка или другая дека могут ещё использовать её. Для ожидания первого streamable файла также нужен выход по отмене.

**Что затронуть:** `PcmCache.Entry/startDecode/cancelEntry`, callback в playback routes, `PublicMusic.playbackInput`, тесты progressive audio/shared preparation/transfer cancellation.

**Критерий пользы:** два оставленных трека не задерживают третий; после ухода последнего потребителя upstream прекращается, при оставшемся потребителе продолжается. Измерять активные процессы и оставшиеся после отмены байты в синтетическом медленном сервере. PCM действующего потребителя должен совпадать с эталоном.

### 4. Остановка анализатора не завершает подготовку его заданий

**Код:** [analysis.ts:286](../apps/server/src/analysis.ts#L286), 286–291, а также 172–188; [app.ts:180](../apps/server/src/app.ts#L180), 180–182. Дополнительный незавершённый путь: `apps/server/src/providers/yandex.ts:497` не принимает переданный registry сигнал; `apps/server/src/providers/index.ts:49` его передаёт.

Обычный `cancel()` выставляет `r.abort` и shared atomic flag. `stop()` делает только `postMessage(cancel)`, ждёт 100 мс и `terminate()` workers. Если worker ещё ждёт `resolveMediaPath`, его `cancel` сообщение ничего не останавливает, а parent callback продолжает работу после окончания `stop()`. В самопроверке `AbortSignal` остаётся неотменённым, поздний callback посылает новое `job` уже после `terminate`.

В приложении сразу после `analysis.stop()` закрывается БД. Поздняя подготовка может попытаться читать/обновлять её либо оставить загрузку до принудительного выхода. Это **риск shutdown**, а не воспроизведённое повреждение БД. `publicMusic.stop()` раньше в shutdown закрывает часть YouTube/SoundCloud путей, но не все provider-операции. У Яндекса `fetchAudio` вообще теряет сигнал, поэтому одного добавления `r.abort.abort()` недостаточно для гарантированного освобождения всех ресурсов.

**Минимальное исправление:** отменять preparation controllers и atomic flags, хранить/ожидать обещания подготовок, проверять остановку перед изменением хэша и отправкой job; закрывать БД только после завершения callbacks. Протянуть отмену через Yandex audio с учётом общей загрузки. Фиксированная задержка 100 мс не является подтверждением завершения.

**Что затронуть:** lifecycle `AnalysisService`, shutdown приложения, отменяемые provider-операции; отдельные тесты остановки во время resolve, после resolve и внутри CPU-анализа.

**Критерий пользы:** после разрешения `stop()` не возникает новых job, SQL-вызовов и загрузок. Повторить с поздним успехом и поздним отказом источника; проверять отсутствие необработанных rejection. Не менять рассчитанные значения анализа. Официальный контракт [`Worker.terminate()`](https://nodejs.org/api/worker_threads.html#workerterminate) относится к завершению worker; parent promises должны завершаться отдельным протоколом.

### 5. Двойное нажатие Download отменяло смысл Cancel — исправлено

**Исходный код:** `apps/desktop/src/app-update.mjs:62` содержал `if (this.pending) { await this.pending; return this.download(); }`.

После первого `download()` второй вызов ждал его окончания. `cancel()` отменял первый token; первый finally возвращал фазу `available`. Второй вызов рекурсивно входил в `download()`, заново проверял обновление и запускал загрузку с новым token. Это лишняя загрузка крупного установщика после явной отмены, а не самовольная установка.

**Исходное подтверждение:** управляемый updater, два вызова download, cancel, затем завершение первой операции. Получены два вызова `downloadUpdate`, отменённый первый token и финальная фаза `downloaded`.

**Исправление основного ассистента:** теперь строка 62 возвращает текущую `pending` без рекурсии. Существующий тест отмены дополнен вторым ожидающим вызовом; оба получают `available`, загрузка/проверка выполняются ровно по одному разу. Отдельный последующий пользовательский Download по-прежнему работает.

**Независимая проверка после исправления:** `app-update.test.ts` и `app-update-download.test.ts` — 7 тестов прошли. Второй использует настоящий NSIS updater с локальным синтетическим HTTP feed и проверкой SHA-512; установщик не исполнялся. Исправленный модуль побайтно одинаков в music и MORA-github. Основной ассистент готовит его для 0.3.15; публикация и установка этого релиза аудитором не проверялись.

Временный тест аудитора намеренно утверждает старое проблемное поведение; его нельзя использовать как зелёный регрессионный тест после исправления. Для текущего состояния использовать production-тест отмены.

### 6. Анализ длинных записей сохраняет полный mono PCM без лимита

**Код:** [analyzePcm.ts:26](../packages/core/src/mir/analyzePcm.ts#L26) и 68–72; [analyze.ts:126](../packages/core/src/mir/analyze.ts#L126); `apps/server/src/config.ts:60`; `apps/server/src/analysis.ts:58–63`.

Начальное выделение ограничено 600 секундами, но это только начальная ёмкость. `push()` сохраняет всю запись в mono 22050 Hz f32, удваивая массив и копируя старый. Стандартная конфигурация допускает два analysis workers. Для отдельных стадий также создаётся копия mono (`drumEnvelopes`). Кэш результатов и ограничение числа workers не ограничивают объём одной длинной записи.

**Расчёт, не измерение:** 3 часа mono требуют 22050 × 10800 × 4 = 952 560 000 байт полезных сэмплов. При текущем росте от 600 секунд финальная ёмкость — 1 693 571 072 байта, около 1,58 GiB на worker. Во время последнего роста одновременно существуют старый массив и новый, суммарно около 2,37 GiB, не считая прочих данных. Два таких анализа способны создать существенную нагрузку на 4–8 GB ПК. Реальный пик RSS, своп и OOM не измерялись. Локальные длинные файлы доступны независимо от сетевых ограничений размера.

**Минимальное улучшение:** сначала ограничить параллельность тяжёлых заданий по оценке duration/PCM bytes, чтобы длинные записи не анализировались вдвоём, и не запускать заведомо превышающее бюджет задание автоматически. Это не меняет PCM или алгоритм, но может увеличить ожидание анализа; в интерфейсе нельзя обозначать такой анализ как завершённый. Само воспроизведение должно оставаться доступным. Для последующего улучшения длинных записей отдельно рассмотреть ограниченные окна/потоковую обработку MIR, предварительно определив требования к точности; это уже не маленький фикс.

Не считать `Worker.resourceLimits` достаточным ограничителем typed arrays: официальный [Node.js API](https://nodejs.org/api/worker_threads.html#new-workerfilename-options) прямо исключает `ArrayBuffer` из этих лимитов.

**Что затронуть:** admission в AnalysisService и тест расчётного бюджета; только после замеров — устройство MIR accumulator. Не снижать sample rate воспроизведения и не переводить float PCM в int16 ради памяти.

**Критерий пользы:** отдельный согласованный тест длинного синтетического файла с записью RSS/arrayBuffers, времени анализа, event-loop lag и underrun. Для изменения одной лишь очереди результаты анализа должны быть одинаковыми; для изменения MIR нужны эталонные планы/кривые и слуховые проверки переходов. Массовый прогон медиатеки для этого не нужен.

## Что уже сделано разумно

- Worklet использует ограниченные PCM-окна; controller передаёт канальные ArrayBuffer как transferables. Полной копии каждого трека в renderer не обнаружено.
- `PcmCache` учитывает readers/pins при вытеснении, использует уникальные `.part` и защищён от открытия файла в момент rename.
- Полные результаты анализа ограничены LRU из 64 элементов; проблема длинного активного анализа отличается от размера этого LRU.
- `EventHub` отключает клиента, у которого очередь вывода превысила 256 KiB.
- Обновлятор не скачивает автоматически, проверяет целостность и не устанавливается без отдельного действия. Реальные проверки corrupted download/cache прошли.

Эти наблюдения не доказывают отсутствие прочих дефектов. Они означают, что переписывать систему кэшей/движок целиком ради найденных проблем не требуется.

3. После параллельных изменений текущего дерева повторены 4 оставшиеся самопроверки — все подтвердили поведение. Updater исключён из старого bug-reproducer.
4. После исправления updater повторены 2 production-файла, 7 тестов — прошли, включая обновлённый сценарий второго Download при Cancel.

Временные проверки находятся в `tools/.cache/fresh-audit-20261023/resource.test.ts`, конфигурация рядом. Команда для повторения только оставшихся четырёх сценариев:

```powershell
node node_modules/vitest/vitest.mjs run --config tools/.cache/fresh-audit-20261023/vitest.config.mjs --maxWorkers=2 -t 'orphaned|submitted after|authoritative|staying alive'
```
